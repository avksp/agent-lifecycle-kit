# Проверка нейтральности

Проверка нейтральности не позволяет секретам репозитория, локальным путям и
материалам конкретного хоста попасть в переносимые подтверждения выпуска. Для
выпуска используется область `tracked-release`:

```bash
agent-lifecycle-neutrality scan \
  --scope tracked-release \
  --policy policy/neutrality.policy.json \
  --require-zero-findings
```

Равнозначный запуск через модуль: `python -m agent_lifecycle.neutrality`.

## Выбор области

| Область | Источник | Назначение |
| --- | --- | --- |
| `tracked-release` | Записи индекса Git из `git ls-files -z --stage --cached` и идентификатор текущего `HEAD` | Непрерывная интеграция, подготовка выпуска и проверка переносимого исходного дерева. |
| `current-tree-complete` | Обычные файлы рабочего дерева | Совместимость со старыми локальными проверками. Для выпуска не рекомендуется. |
| `full-repository` | Файлы рабочего дерева и доступные объекты Git | Совместимость со старыми углублёнными проверками. Для выпуска не рекомендуется. |

Область `tracked-release` не заходит во вложенные репозитории. Обычный файл
читается как файл, у отслеживаемой символьной ссылки проверяется только её
содержимое без перехода к цели, а ссылка на вложенный репозиторий связывается с
идентификатором объекта из индекса. Отсутствующая, несведённая, повреждённая
или неизвестная запись делает проверку неполной.

Проверяются все отслеживаемые пути, в том числе те, которые старая проверка
рабочего дерева исключала через `pathExcludes`: отслеживаемый файл является
частью выпуска. Команды Git запускаются через доверенный набор инструментов
хоста с ограничением времени, а дерево и индекс не должны изменяться во время
проверки выпуска.

В `scopeBinding` отчёт связывает область, класс источника, текущую ревизию и
отпечаток записей индекса. Старые области остаются допустимыми, но в их
подписанной привязке записывается `deprecatedScope: true`.

## Производительность и полнота в 1.78

`tracked-release` остаётся обычным маршрутом для выпуска. Если план явно
требует `full-repository`, объекты Git читаются через ограниченные пакетные
потоки: перед сопоставлением проверяются принятая инвентаризация,
идентификаторы и типы объектов, их размеры и обрамление протокола. Тайм-аут,
повреждённый ответ, превышение лимита или обрезанный объект дают неполное
подтверждение; сканер не исключает объект молча и не объявляет частичную
проверку чистой.

Правила запрета из полномочий и политики проверяются до сопоставления по общим
ограничениям количества, длины и суммарного размера. Сопоставление строк
сохраняет идентификаторы правил, порядок находок и дубликаты; регулярные
выражения сохраняют отдельную семантику. Данные производительности являются
справочными, если план явно не сделал конкретный предел критерием приёмки. См.
[бюджеты производительности и ресурсов](performance-and-resource-budgets.md).

## Локальные материалы

Игнорируемые и неотслеживаемые подтверждения по умолчанию не читаются. Для
отдельной проверки их можно включить явно:

```bash
agent-lifecycle-neutrality scan \
  --scope tracked-release \
  --policy policy/neutrality.policy.json \
  --include-local-artifacts \
  --require-zero-findings
```

Флаг не принимает произвольные пути. Проверяются только относительные корни из
поля политики `localArtifactRoots`. Они должны оставаться внутри рабочего
дерева; переход через символьные ссылки запрещён. Намерение включить локальные
материалы, разрешённые корни, их отпечаток, счётчики файлов и отпечаток
содержимого входят в подписываемую часть отчёта.

Обычная проверка выпуска должна использовать `tracked-release` без этого
флага. Включайте локальные материалы только в специально предназначенном шаге
с подтверждениями.

Объявленные локальные корни должны существовать, не содержать символических
ссылок и вложенных каталогов `.git`, а также укладываться в ограничения
`maxLocalArtifactFiles` и `maxLocalArtifactBytes`. Пути сортируются, поэтому
неизменившийся корень даёт одинаковый отпечаток при повторной проверке.

## Устойчивое чтение

Состояние обычного файла или содержимого символьной ссылки проверяется до и
после чтения. При первом изменении выполняется ровно одна повторная попытка.
Успешная повторная попытка увеличивает информационный счётчик
`recoveredReadRaces`, который также входит в подписываемую часть отчёта. Если
объект изменился снова, увеличиваются `readRaces` и `incompleteScans`,
неустойчивые данные исключаются, а обязательная чистая проверка завершается
отказом.

Чистота определяется единым набором `REQUIRED_COMPLETENESS_COUNTERS`.
Информационный счётчик `recoveredReadRaces` сам по себе не делает чистый отчёт
ошибочным.

## Подписанные маршруты

Одинаковые области и флаг локальных материалов доступны в командах `scan`,
`bootstrap` и в шлюзе нейтральности контроллера. Отдельная подписанная
квитанция и квитанция шлюза связывают `scopeBinding`, `deprecatedScope`,
отпечаток предмета проверки и обязательные счётчики. Изменение области,
ревизии, отпечатка индекса, намерения включить локальные материалы или списка
разрешённых корней нарушает проверку подписи.

Материалы полномочий и подписи по-прежнему предоставляет хост. Правила доверия
и запрета замены файлов описаны в
[контракте нейтральности](../security/neutrality-contract.md).
