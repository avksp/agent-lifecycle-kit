# Учёт расхода жизненного цикла

Учёт расхода показывает, сколько токенов и шагов ушло на непосредственное
решение задачи, проверку продукта, соблюдение жизненного цикла и координацию.

## Зачем это нужно

ALK должен помогать внешнему агенту довести задачу до проверяемого результата,
а не заменять работу созданием служебных артефактов. Поэтому отчёт разделяет
четыре категории: `implementation`, `productValidation`,
`pipelineCompliance` и `coordination`.

Первые две категории относятся к созданию и проверке продуктового результата.
Категория `pipelineCompliance` охватывает планирование, фиксацию плана,
проверку владения, аудит жизненного цикла и итоговое доказательство.
Категория `coordination` учитывает маршрутизацию, передачу работы и действия по
состоянию, которые сами по себе не создают результат.

## Команды

```bash
agent-lifecycle metrics cost-report \
  --mode standard \
  --artifact work/run/usage.json \
  --artifact work/run/task-review.json \
  --out work/run/lifecycle-cost.json

agent-lifecycle metrics cost-check --receipt work/run/lifecycle-cost.json
```

Команда `cost-report` читает существующие подтверждения и создаёт отчёт без
изменения рабочего состояния. `cost-check` проверяет категории, числа,
ограничения выбранного режима и достоверность сведений об использовании.

Дополнительная команда `metrics recommend` предлагает режим жизненного цикла
на основе накопленных отчётов. `policy adaptive-decision` учитывает форму
задачи, уровень SDD, риски, обязательные подтверждения, число попыток, размер
контекста и ограничения ресурсов. Эти команды ничего не применяют
автоматически. Запись предложения правила требует одновременных параметров
`--apply` и `--output`.

## Что проверяется автоматически

Для режимов `light`, `standard`, `strict` и `release` заданы ограничения на
долю токенов и шагов категории `pipelineCompliance`, а также на её абсолютный
размер. Превышение без объяснения `overLimitReason` делает проверку
неуспешной.

Текущая проверка не включает `coordination` в долю
`pipelineCompliance`. Поэтому успешный отчёт подтверждает соблюдение
объявленных ограничений процесса, но сам по себе не доказывает, что все
служебные затраты занимают меньше половины реального запуска. Для такого
вывода нужны полные данные хоста по этапам и совместная оценка обеих категорий.

Если в обычной задаче S0 или S1 служебная работа преобладает, следует убрать
дублирующие проверки, сократить необязательную перепроверку, разделить слишком
широкий план или отказаться от ALK для этой задачи. Задачи с подтверждённым
риском могут требовать более строгого процесса, но причина превышения должна
быть записана явно.

USD-поля не обязательны для локальных моделей и моделей по подписке. Если
тарифицируемый хост требует раннего запроса оператора, `meteredAskThreshold`
указывается только в бюджетной политике тарифицируемого режима и остаётся
рекомендательным; жёсткий лимит всё равно определяет, нужно ли останавливать
выполнение.

Адаптивная политика принимает денежные метаданные только для
`budgetMode: "metered"` и не использует их для выбора режима. Решение выбирается
по токенам, времени, числу вызовов, повторам и минимальному уровню качества.

## Ограничение качества

Экономия не должна отключать обязательные проверки для релизов, адаптеров,
контрактов, миграций, задач с рисками безопасности и работ уровня S2.
