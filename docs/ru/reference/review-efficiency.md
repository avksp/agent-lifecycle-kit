# Эффективность проверки

Подтверждение эффективности показывает, где аудит расходует время и токены,
не снижая review, security, architecture или quality gates. Это
рекомендательное представление учёта, а не право принять задачу или применить
оптимизацию.

## Команда

Постройте отчёт из явного артефакта `agent-audit-efficiency-input.v1`:

```bash
agent-lifecycle metrics audit-efficiency \
  --input work/accounting/release-2-7.json \
  --comparison work/accounting/release-2-6.json \
  --out work/accounting/audit-efficiency.json
```

Параметр `--comparison` можно повторять. Каждый вход проверяется до
create-only записи результата. Повреждённый digest, придуманное значение,
неверный статус или невалидное сравнение приводят к отказу.

Команда создаёт `agent-audit-efficiency-report.v1`. Его поля полномочий всегда
равны `qualityFloorPreserved: true`, `advisoryOnly: true`, `autoApply: false` и
`productionPromotionClaimed: false`.

## Семантика доступности

Каждая метрика имеет статус `MEASURED`, `ESTIMATED`, `TIME_WINDOW_ONLY`,
`MIXED` или `UNAVAILABLE`. У недоступной метрики `value: null`; она никогда не
превращается в ноль. Четыре представления остаются раздельными:

- `alkProcess`;
- `implementation`;
- `audit`;
- `postAuditRemediation`.

Отчёт содержит подтверждённые и отклонённые находки, сеансы без вердикта,
число аудитов и исправлений. Производные метрики показывают токены и время на
подтверждённую находку, долю работы без влияния на acceptance, долю
отклонённых находок и долю исправлений после аудита.

## Сравнение

Один валидный релиз возвращает `NO_COMPARISON` и не может выдавать процент
снижения токенов или времени. Для сравнения нужны минимум два привязанных к
lineage входа с одинаковым quality floor и полной сопоставимой телеметрией.
Отсутствующие данные реализации или контроллера остаются `UNAVAILABLE` и
блокируют процент, а не ослабляют требование к доказательствам.

Отслеживаемая фикстура Release 2.6 сохраняет наблюдавшийся baseline:
`29,195,208` токенов аудита, `9,278,567 ms` wall time и `12,228,901 ms`
compute time. Токены вне аудита в ней `UNAVAILABLE`, а не ноль.

Отслеживаемый baseline дельта-аудита Release 2.12 следует тому же правилу. В
нём сохранены измеренный вход полного повторного аудита, сырые счётчики токенов
и время, но маршрут дельта-аудита для той же истории и проценты сокращения
помечены `UNAVAILABLE`, поскольку этот маршрут не использовался для приёмки.
Наблюдавшийся fallback на `FULL_AUDIT` остаётся видимым. Поздний сопоставимый
запуск может добавить отсутствующую сторону, но не восстанавливать её по
размеру prompt или другому сеансу.

## Связь с оптимизацией

[Оптимизация проверок по подтверждённым данным](audit-optimization.md)
оценивает будущие профили и holdout-задачи. Эффективность проверки объясняет
измеренные расходы и исходы. Ни один маршрут автоматически не меняет активный
профиль, зафиксированный план, результат задачи или вердикт проверки.

Статистические заявления должны соответствовать
[независимости подтверждений](evidence-independence.md). Acceptance раунда и
disposition находок остаются в границах [Review Mesh](review-mesh.md).
