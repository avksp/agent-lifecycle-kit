# Маршрутизация моделей

Маршрутизация моделей выбирает нейтральный класс модели для этапа жизненного
цикла или попытки задачи. Она не вызывает API провайдера и не записывает
конкретные имена моделей в переносимые планы, пакеты задач, lock-файлы или
состояние workflow.

```bash
agent-lifecycle model profile-check \
  --profile profiles/model-routing-profile.v1.json

agent-lifecycle model profile-check \
  --type host \
  --profile <host-model-profile.json>

agent-lifecycle model route \
  --profile profiles/model-routing-profile.v1.json \
  --host-profile <host-model-profile.json> \
  --request <model-route-request.json>

agent-lifecycle model usage-check \
  --receipt <model-usage-receipt.json> \
  --route-decision <model-route-decision.json> \
  --budget-targets conformance/core/budget-targets.v1.json
```

`model route` детерминирован: одинаковый запрос и одинаковые профили дают один
и тот же отпечаток решения. Сигналы ошибок могут повышать класс модели, но не
понижают его ниже уже выбранного безопасного уровня.

Классы моделей остаются нейтральными: `no-model`, `budget`, `local-compact`,
`standard-code`, `local-standard-code`, `strong-reasoning`,
`local-strong-review` и `specialist-review`. Конкретные имена моделей хранятся
только в локальных профилях хоста и могут быть замаскированы или не
коммититься.

Для операций с моделью нужен `agent-lifecycle-model-usage-receipt.v1`, привязанный
к тому же запуску, задаче, попытке, отпечатку плана, исходной ревизии и
решению маршрутизации.

Обычное подтверждение содержит `inputTokens`, `outputTokens`,
`billableTokens`, `cumulativeContextBytes`, `toolCalls` и `wallSeconds`.
Для попытки с учётом риска добавляется `usage.invocations`. Профиль проверяет
`billableTokens`, `invocations` и `wallSeconds`; превышение любого ограничения
отклоняет `workflow task-result`.

Дополнительное поле обязательно только после разрешения попытки командой
`workflow task-start --risk-profile <path>`. Полный сценарий приведён в разделе
[Запуск с учётом риска](risk-aware-execution.md).

Локальный нормализатор адаптера может сформировать то же подтверждение как
сопутствующий результат, не меняя схему операции хоста. Ядро принимает его как
подтверждённый расход только при одновременном наличии `source: host`,
`status: ATTESTED` и принятого состояния нормализатора. Подробнее:
[локальный учёт токенов хоста](host-local-token-accounting.md).

## Связки исполнения по этапам

Необязательная локальная связка соединяет нейтральный класс этапа с конкретными
адаптером, профилем модели, профилем запуска и reasoning effort. Существующий
resolver проверяет риск, контекст, данные, возможности и независимость. У этапа
может быть до трёх разрешённых связок, включая основную. Разные этапы могут
использовать разные записи реестра, содержащего до 32 связок.

Начните с обнаружения CLI или передайте ручной черновик:

```sh
agent-lifecycle model setup --discover --scope project
agent-lifecycle model setup --manual --input local-bindings.json --scope project
```

Ручной вход — закрытый объект с полями `projectProfile` и `registry`.
`projectProfile` — обычный профиль рабочего процесса проекта. `registry`
использует `agent-local-stage-bindings.v1` и объект `bindings`, ключи которого —
локальные идентификаторы. Каждая запись содержит:

| Поле | Содержание |
| --- | --- |
| `adapterId` | Идентификатор существующего адаптера. |
| `hostModelProfile` | Допустимые `path`, исходный `sha256` и нейтральный `modelClass`. |
| `launchProfile` | Допустимые `path` и исходный `sha256` существующего профиля запуска. |
| `hostParameters` | Точный `reasoningEffort`, без скрытой замены значения. |
| `parameterSupport` | `allowedEfforts` и ссылка `evidence` с путём/хэшем документации заявленной поддержки. |
| `qualificationEvidence` | Путь/хэш штатной квитанции квалификации запуска для точной версии CLI. |

Связанные файлы находятся внутри `.alk/host-launch`. Имена моделей остаются в
существующем профиле модели хоста. Заявленная поддержка параметра сама по себе
не подтверждает доступность или пригодность модели. Недостающая настройка
возвращает `MISSING_INPUT`. Обнаружение проверяет известные CLI с конечными
лимитами процессов, времени и вывода. Оно не устанавливает программы, не читает
учётные данные, не выполняет вход и не вызывает модели. Если хост не поддерживает
список моделей, используйте ручной ввод с непроверенным статусом. Наличие CLI
не означает доступность модели.

Оба варианта настройки работают без записи до явного применения:

```sh
agent-lifecycle model setup --manual --input local-bindings.json --scope project --apply --expected-profile-digest CURRENT_RAW_SHA256
```

Для первого создания укажите `ABSENT` вместо текущего исходного SHA256 файла.
Применение создаёт неизменяемый реестр и последней фиксирует ссылку профиля
проекта. Изменившийся профиль, небезопасный путь и конфликт результата вызывают
отказ. Используется область проекта; глобальные настройки пользователя не меняются.

Просмотрите выбор для этапа и проверьте связку без вызова модели:

```sh
agent-lifecycle model explain --stage implementation --project-profile .alk/project-profile.json --request route-request.json
agent-lifecycle model availability --binding primary --project-profile .alk/project-profile.json
```

Локальное представление показывает модель, effort и причины принятия или отказа
каждому кандидату. Параметр `--portable` выводит нейтральные классы, отпечатки и
коды причин без локальных имён и argv. Сохраняются отдельные состояния CLI,
настройки, авторизации, probe и качества задачи. Недоступное значение не равно
нулю. Порядок приоритетов задаёте вы; ALK не обещает самую дешёвую или лучшую модель.

### Первая проба и native-исполнение

Подготовьте новый обычный локальный профиль для фактической версии CLI и один
раз выполните `agent-lifecycle host-launch preflight --profile LOCAL_PROFILE`.
Каноническая квитанция связывает этот профиль, исполняемый файл и версию.
В `qualificationEvidence` укажите именно штатную квитанцию политики профиля.
Она не подтверждает вызов модели, её доступность или качество задачи.

Явная ограниченная проба может получить первое наблюдение доступности:

```sh
agent-lifecycle model availability --binding primary   --project-profile .alk/project-profile.json --probe   --authorization-receipt work/execution-authorization.json   --state work/run.state.json --manifest plans/feature/plan.manifest.json   --lock plans/feature/plan.lock.json --task WS-01   --operation-id PROBE_OPERATION --expected-revision REV --source-revision SOURCE_SHA   --max-invocations 1 --max-wall-seconds 60 --max-output-bytes 65536
```

Передайте актуальные привязки и разрешение на диагностику. Первой пробе может
не хватать прежнего положительного наблюдения доступности; все проверки native
authorization, профиля, риска, исходников и первоначального deadline обязательны.
Проба не принимает задачу и не меняет активную связку реализации. Для обычного
автоматического выбора нужны требуемые свежие доказательства. Отдельная
managed-задача с независимой приёмкой подтверждает поддержанный сценарий задачи.

Резерв выбирается до начала попытки только при доказанной недоступности до
dispatch, среди заранее разрешённых подходящих связок. Активная попытка сохраняет
свою связку. Неизвестный старт, timeout или потеря ответа требуют сверки либо
блокировки, без слепой повторной отправки. Ошибки кода и тестов идут в remediation.
Сохраняются попытки, исходные deadlines и расходы. Один CLI-вызов может содержать
несколько запросов провайдера; неизвестные токены, запросы и цена остаются недоступны.

Поддержка native-маршрута зависит от точной локальной квалификации. Первый consumer
связок использует обычный маршрут Codex. Остальные хосты требуют своих доказательств;
отдельный `codex-exact-prompt-v1` отказывает в этом opt-in. Модель текущего
координатора не меняется. См. [профили рабочего процесса](project-workflow-profile.md)
и [границу SDLC](../architecture/sdlc-boundary.md).

### Принять связку перед запуском

Выбор связки и допуск попытки — отдельные операции. Для зафиксированной задачи
реализации передайте `start --strategy-out PATH`, актуальный этап, профиль проекта
и полные привязки workflow. Подготовка создаёт артефакт стратегии, но не вызывает
хост и не разрешает исполнение. Затем используйте существующий
`workflow task-start --strategy PATH` с обязательными доверенными входами политики
и профилей. Штатный переход заново проверяет и сохраняет только нейтральную
идентичность связки и конфигурации. После этого `start --launch` использует ту же
сохранённую идентичность. Активная попытка без привязки или с другой связкой
вызывает отказ; изменение локальной настройки не меняет попытку молча.
При отсутствии допуска используйте возвращённую точную команду подготовки.
Проекция managed workflow работает только на чтение и не начинает попытку.

Неизвестное, просроченное или изменившееся наблюдение основного маршрута блокирует выбор и требует явно разрешённого ограниченного probe. Оно не доказывает недоступность для перехода к резерву. Положительный probe требует полного успешного JSONL-ответа Codex с сообщением модели и завершением хода. Кода выхода 0, справки или версии недостаточно. Идентичность модели на сервере и effort остаются неподтверждёнными.

## Завершение по объявленным источникам при неполном учёте хоста

Для модельной попытки нужна квитанция расходов до `workflow task-result`.
Успешный ответ модели или probe доступности её не заменяет. По умолчанию
действует контракт учёта, выбранный замороженным планом.

Проверенный замороженный план может явно выбрать `SOURCE_AUTHORING_LIMITED`
с `alk-source-usage-completion-policy.v2` и `PROJECT_DECLARED_SOURCE`. Этот
опциональный маршрут использует исходные объявленные данные учёта, замороженный
префикс источников и отдельный допуск для каждой попытки задачи. Источник сохраняет
прежние объявленные единицы, известные частичные данные, неизвестные интервалы
и исходные часы. Служебное списание не является измеренным числом токенов или
суммой счёта. Финансовый Journal по-прежнему отказывает в резервировании при
неполных начальных данных; новый маршрут этого правила не меняет.

Существующая квитанция usage v2 содержит `null` и `UNAVAILABLE` для всех семи
метрик полного расхода хоста. Её attestation — `alk-declared` / `UNAVAILABLE`.
Соответствие фактическим лимитам остаётся `UNAVAILABLE`, финансовое закрытие —
`OPEN_UNAVAILABLE`. Независимая проверка, типизированный аудит, приёмка задачи
и финализация обязательны. Нативное завершение по этому ограниченному контракту
не означает финансового расчёта. Обязательный жёсткий лимит, который нельзя
наблюдать, по-прежнему блокирует выполнение.

Данные источника готовит `workflow source-usage-prepare`. Для открытия нужны
исходные данные и явные привязки исполнителей, ролей и задач. Фазы admission
и receipt проверяют текущий замороженный план, авторизацию, исходники, попытку
и состояние учёта. Текущую запись учёта выбирает замороженная политика, а не
квитанция. Храните исходные снимки локально и сохраняйте точные байты в `.raw`.
Новые структурированные артефакты записываются как канонический JSON. Изменение
источника, префикса, исполнителя, binding или состояния учёта требует отказа либо
явного восстановления. Режим не включается автоматически при отсутствии или
отказе квитанции v1.
