# Локальный запуск внешней команды

Локальный запуск внешней команды предназначен для опытного пользователя. Он
позволяет явно запустить один внешний процесс после того, как ALK принял
полностью связанный зафиксированный запуск. Уровень поддержки адаптера,
учётная запись хоста и текст задачи остаются в своих объявленных границах:
механизм не подставляет текст задачи и не
превращает адаптер со статусом `WRAPPER_ONLY` в официально поддерживаемое
средство прямого запуска.

Изменения производительности в релизе 1.78 не ослабляют эту границу: результат
проверки профиля не кэшируется, ограничения процесса и очистка остаются
обязательными, а данные производительности не выдают полномочия на запуск. См.
[бюджеты производительности и ресурсов](performance-and-resource-budgets.md).

Профиль принадлежит пользователю и должен находиться в `.alk/host-launch/`.
Весь каталог `.alk/` исключён из Git.
Идентификатор публичной схемы: `agent-local-host-launch-profile.v1`.

## Создание локального профиля

Для Codex `0.147.0`, Claude Code `2.1.226` и OpenCode `1.18.15` используйте
поставляемый профиль с точной привязкой к версии из раздела [запуск
зафиксированной задачи через проверенный профиль](qualified-host-launch.md).
Ручной формат ниже предназначен для пользовательской обёртки и сам по себе не
подтверждает поддержку внешнего инструмента.

Создайте `.alk/host-launch/codex.json`:

```json
{
  "schemaVersion": "agent-local-host-launch-profile.v1",
  "status": "LOCAL_OPT_IN",
  "adapterId": "codex",
  "executable": "codex",
  "argvTemplate": [],
  "versionProbeArgs": ["--version"],
  "env": {
    "allow": ["HOME", "PATH"],
    "allowPatterns": [],
    "projectPolicyAllowed": false
  },
  "timeoutSeconds": 30,
  "shell": false,
  "writesNativeConfig": false,
  "promptInjectionDefault": false,
  "publicSupportClaimed": false,
  "productionPromotionClaimed": false
}
```

Поле `executable` содержит один элемент команды, а не командную строку.
Командные оболочки, выход из каталога через относительный путь, шаблоны имён
переменных окружения, частичная подстановка и неизвестные подстановки
отклоняются.

Поле `versionProbeArgs` допускает только `--version`, `-V` или `version`. Для
имени исполняемого файла без абсолютного пути переменная `PATH` должна быть в
точном списке разрешённого окружения. Поэтому `preflight` остаётся проверкой
версии и не превращается в средство запуска произвольной команды.

В `argvTemplate` допустимы постоянные элементы и следующие подстановки,
занимающие элемент целиком:

- `{adapter_id}`;
- `{state_path}`, `{manifest_path}` и `{lock_path}`;
- `{task_id}`, `{operation_id}` и `{source_revision}`;
- `{risk_profile_digest}`.

Текст задачи намеренно не входит в этот список. Профиль может запустить
установленный внешний инструмент или локальную обёртку, но не может незаметно
передать непроверенный запрос через аргументы процесса.

## Проверка профиля и готовности

Следующая команда проверяет путь, структуру и отпечаток профиля, не создавая
процесс:

```bash
agent-lifecycle host-launch inspect \
  --profile .alk/host-launch/codex.json
```

Проверка готовности явно запускает указанный исполняемый файл один раз только с
аргументами из `versionProbeArgs`. Время проверки ограничено 10 секундами, даже
если для основного запуска указано большее значение:

```bash
agent-lifecycle host-launch preflight \
  --profile .alk/host-launch/codex.json
```

Подтверждение содержит `processCalls: 1`, отпечаток профиля, код завершения и
очищенный вывод. Если команда не установлена, завершилась с ошибкой или
превысила время, ALK возвращает структурированную ошибку.

Для поставляемого проверенного профиля эта команда также создаёт
`agent-host-launch-qualification-receipt.v1`. Основной запуск требует точного
совпадения отпечатка профиля и версии команды.

## Запуск зафиксированной задачи

Сначала подготовьте полный `agent-adapter-task-run-request.v1`. Его поля
`state`, `manifest`, `lock`, `task`, `operationId`, `expectedRevision` и
`sourceRevision` должны указывать на одну зафиксированную задачу ALK. Для S1/S2
нужен действительный локальный профиль модели, чтобы ALK вывел ограничения по
ресурсам и требования к учёту расхода.

```bash
agent-lifecycle start \
  --adapter codex \
  --mode implement \
  --file work/my-run/adapter-run-request.json \
  --risk auto \
  --host-model-profile profiles/hosts/codex-live-profile.v1.json \
  --launch \
  --host-launch-profile .alk/host-launch/codex.json
```

Непосредственно перед созданием процесса ALK проверяет зафиксированный манифест
и файл блокировки, происхождение состояния, задачу, выведенный профиль риска,
соответствие адаптера и явный флаг `--launch`. До защищённого запуска процесса
доходит только функция `launch_from_local_profile`.

Этот базовый механизм не подставляет текст задачи и не подключается к прежнему
диалогу внешнего инструмента. Специализированная обёртка может использовать
подстановки зафиксированной идентичности, чтобы найти проверенный вход.
Поддержка прямого запуска конкретного внешнего инструмента требует отдельного
подтверждения.

## Условия безопасного отказа

- Обычный текст, Markdown, а также режимы исследования, планирования и проверки
  никогда не запускают процесс.
- `--launch` и `--host-launch-profile` указываются только вместе.
- `host-launch inspect` не создаёт процессы.
- `host-launch preflight` создаёт не более одного ограниченного процесса
  проверки версии.
- `adapter session start --launch` остаётся заблокированной командой.
- `launch_from_descriptor` остаётся заблокированной даже для пользовательского
  дескриптора со статусом `SUPPORTED`.
- Значения окружения выбираются только по точным именам и не записываются в
  подтверждения.
- Вывод процесса, локальные пути в аргументах и ошибки запуска очищаются общим
  механизмом ALK.

См. [управляемые сессии адаптеров](managed-adapter-sessions.md), [запуск с
учётом риска](risk-aware-execution.md) и [матрицу поддержки
адаптеров](../adapters/support-matrix.md).
