# Оптимизация проверок по подтверждённым данным

[English version](https://github.com/avksp/agent-lifecycle-kit/blob/main/docs/reference/audit-optimization.md)

Оптимизация проверок по подтверждённым данным помогает настраивать повторные
проверки ALK по локальным артефактам выполнения. Она объединяет результаты по
качеству с временем ожидания, повторами, тайм-аутами, токенами, процессорным
временем, памятью и числом процессов. Итогом становится ограниченная
рекомендация для будущей работы; действующий план не меняется.

Этот процесс полезен, когда регулярно проверяются задачи одного типа, команда
сравнивает большие, малые или локальные модели либо независимая группа
проверяющих стала работать слишком медленно или дорого. Для одной новой задачи
без накопленных данных используйте обычный жизненный цикл и сначала соберите
подтверждения.

## Что измеряется

Оптимизатор читает явные локальные наборы подтверждений и сохраняет только
ограниченное представление:

- форму задачи, этап, класс маршрута и отпечаток формы запроса;
- статус проверки, число найденных проблем, их серьёзность и статус
  независимости;
- результаты по успешному завершению, блокировкам, исправлениям,
  разногласиям и ошибочным приёмкам;
- число попыток, повторов и тайм-аутов;
- подтверждённые входные, выходные и оплачиваемые токены и время выполнения;
- подтверждённые процессорное время, пиковую память и число процессов.

В артефакты попадают отпечатки и счётчики, но не запросы, стенограммы,
вывод хоста, секреты, имена провайдеров и моделей или абсолютные локальные
пути. Если хост не предоставляет данные об использовании или ресурсах,
результат помечается как недоступный, а уверенность снижается.

## Порядок работы

### 1. Соберите локальную выборку

Передайте наборы подтверждений завершённых проверок. Команда не обращается к
хосту и модели:

```bash
agent-lifecycle metrics audit-sample \
  --receipt work/review-01/receipt-bundle.json \
  --receipt work/review-02/receipt-bundle.json \
  --receipt work/review-03/receipt-bundle.json \
  --out work/audit-optimization/samples.json
```

Каждый вход может содержать подтверждения проверки, использования модели,
выполнения процесса и результата одной операции. На выходе создаётся
`agent-audit-optimization-sample-batch.v1` с отпечатком и явными признаками
соблюдения границ данных.

### 2. Опишите профиль-кандидат

Кандидат описывает будущий профиль, а не меняет работающий процесс. Например:

```json
{
  "profileId": "feature-review-balanced",
  "taskShape": "feature",
  "qualityFloor": "standard",
  "routeClass": "standard",
  "packetTokenLimit": 12000,
  "reviewerCountHint": 2,
  "timeoutSeconds": 900,
  "retryLimit": 1,
  "holdoutTasks": [
    {"taskId": "feature-01", "qualityPass": true, "billableTokens": 4200, "wallSeconds": 85},
    {"taskId": "feature-02", "qualityPass": true, "billableTokens": 3900, "wallSeconds": 78},
    {"taskId": "feature-03", "qualityPass": true, "billableTokens": 4500, "wallSeconds": 91}
  ]
}
```

В наборе должно быть не менее трёх разных задач для каждой формы и не более
двенадцати задач в общей проверке. Кандидат допускается только при достижении
требуемого уровня качества и нулевой доле ошибочных приёмок. Для всех
кандидатов в одном отчёте используется один и тот же набор задач.

### 3. Постройте отчёт

```bash
agent-lifecycle metrics audit-report \
  --sample work/audit-optimization/samples.json \
  --candidate-profile profiles/feature-review-balanced.json \
  --task-shape feature \
  --quality-floor standard \
  --out work/audit-optimization/report.json \
  --terminal
```

JSON-артефакт имеет схему `agent-audit-optimization-report.v1`. Краткий вывод
показывает число образцов, уверенность, долю успешных и ошибочных приёмок,
исправления, p50/p95 времени и токенов, выбранный профиль и следующий шаг.
Статус отчёта означает:

- `PASS` — данных достаточно, а кандидат прошёл проверку качества;
- `NO_RECOMMENDATION` — нужно собрать больше данных или все кандидаты не
  прошли контроль качества;
- `FAIL` — входные данные, границы подтверждений или лимит проверки нарушены.

Рекомендация блокируется при низкой уверенности, смешанных подтверждениях,
ошибочной приёмке, повторных исправлениях или снижении обязательного уровня
качества.

### 4. Зафиксируйте решение

Сначала создайте предложение без подтверждения:

```bash
agent-lifecycle metrics audit-proposal \
  --report work/audit-optimization/report.json \
  --target-kind project-profile \
  --target-revision feature-review-v2 \
  --out work/audit-optimization/proposal.json
```

После просмотра отчёта и подтверждений зафиксируйте решение оператора:

```bash
agent-lifecycle metrics audit-proposal \
  --report work/audit-optimization/report.json \
  --approved \
  --target-kind project-profile \
  --target-revision feature-review-v2 \
  --out work/audit-optimization/approved-proposal.json
```

Подтверждение является частью артефакта решения. Оно не изменяет текущий
профиль, манифест плана или lock-файл.

### 5. Создайте новый профильный артефакт

```bash
agent-lifecycle metrics audit-apply \
  --proposal work/audit-optimization/approved-proposal.json \
  --out work/audit-optimization/feature-review-v2.json
```

Команда создаёт новый артефакт `agent-audit-optimization-applied-profile.v1`.
Предыдущий профиль остаётся точкой отката. Для изменения замороженного плана
создаётся новая ревизия, а его манифест и lock-файл этой командой не заменяются.

## Как читать результаты

Для первого сигнала достаточно трёх завершённых проверок с независимыми
подтверждениями. Уровень `MEDIUM` используйте как ориентир для настройки, а
для высокой уверенности соберите не менее шести образцов. Кандидатов сравнивайте
на одном наборе эталонных задач. Выбирайте самую маленькую группу проверяющих,
которая сохраняет обязательный уровень качества; требования S1/S2 нельзя
ослаблять ради экономии времени или токенов.

Для больших моделей отчёт показывает дорогие пакеты, лишние повторы и длинный
хвост времени. Для малых и локальных моделей компактные пакеты и локальные
подтверждения использования сохраняют те же проверки качества, а недоступные
измерения явно отмечаются. Модель и провайдер по-прежнему выбираются адаптером
или профилем хоста.

## Связь с Review Mesh

Review Mesh создаёт назначения, импортирует очищенные результаты проверяющих и
проверяет кворум, если это указано в плане. Оптимизатор читает эти подтверждения
и помогает сравнить будущие профили; он не является новым проверяющим,
контроллером повторов или владельцем кворума. Review Mesh остаётся
необязательным, а одной модели достаточно, если план не требует независимых
измерений.
