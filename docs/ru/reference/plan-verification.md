# Проверка целостности плана

`agent-lifecycle plan verify` - это безопасная проверка передачи пакета плана
другому исполнителю или проверяющему. Команда объединяет проверки, которые
нужны перед использованием зафиксированного плана: форму манифеста, полноту,
трассируемость приёмки, ссылки на репозиторий, требования состояния, lock-файл
и полный состав пакета.

## Команда

Запустите её из репозитория, в котором находится пакет плана:

```bash
agent-lifecycle plan verify \
  --manifest tasks/release-1-79/plan.manifest.json \
  --package-root tasks/release-1-79 \
  --lock tasks/release-1-79/plan.lock.json \
  --acceptance tasks/release-1-79/acceptance-criteria.md \
  --state work/release-1-79/run.state.json \
  --repository-root . \
  --out work/release-1-79/evidence/plan-verification.json
```

Результат имеет контракт `agent-plan-verification-receipt.v1`. Статус `PASS`
означает, что переданный пакет согласован с выбранным статусом плана и
состоянием. Статус `FAIL` содержит структурированные причины блокировки и не
даёт полномочий на изменение кода.

## Что проверяется

- Манифест соответствует `agent-plan-manifest.v1`.
- Требования, критерии приёмки, подтверждения, итоговые гейты и рабочие пакеты
  образуют полный граф без осиротевших элементов.
- Каждый путь полномочий нормализован, задан относительно репозитория и
  указан буквально. Шаблоны с `*`, `?` и `[]`, абсолютные пути, выход через
  `..` и URI-подобные пути отклоняются.
- Для плана `FROZEN` требуется совпадающий lock-файл. Планы `DRAFT` и
  `REOPENED` можно проверять без lock-файла, но переданный lock всё равно
  должен совпадать.
- Для незавершённого состояния рабочего цикла требуется lock-файл. Конечные
  состояния `COMPLETE`, `FAILED` и `CANCELLED` не создают новых полномочий на
  выполнение.
- Если в манифесте объявлена целостность пакета, используется тот же реестр
  `agent-plan-lock.v2`, что и при заморозке. Отдельный алгоритм инвентаризации
  не создаётся.

## Чего команда не делает

Команда не выполняет `validation.commands`, не вызывает модель, не обращается
к сети, не запускает адаптер или процесс хоста и не изменяет состояние рабочего
цикла. Это детерминированная проверка передачи плана, а не аудит реализации и
не решение о выпуске. После появления подтверждений задач запускайте `audit
implementation`, а для совместной проверки плана и реализации - `audit
package`.

## Передача другому проверяющему

Автор плана передаёт другому проверяющему манифест, критерии приёмки, lock-файл
и состояние рабочего цикла. Проверяющий запускает `plan verify`, изучает
результат и выполняет независимый S2-аудит или аудит реализации, который
требует план. Неуспешную проверку исправляют в пакете плана и запускают снова;
текстовый ответ агента сам по себе не заменяет структурированное
подтверждение.
