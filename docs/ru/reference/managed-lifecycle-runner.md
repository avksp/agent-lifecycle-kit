# Управляемый шаг жизненного цикла

`agent-lifecycle workflow run` - ограниченная команда чтения над сохранённым
состоянием жизненного цикла. Она не запускает модель, не запускает процесс
хоста и не меняет состояние. Команда проверяет связь текущего состояния с
зафиксированным планом и возвращает следующий шаг, который должен выполнить
хост.

Это закрывает разрыв между процедурой в skill и CLI: хост может спросить ALK,
что делать дальше, не восстанавливая процесс из текста чата.

## Команда

```bash
agent-lifecycle workflow run \
  --state run.state.json \
  --manifest plans/package/plan.manifest.json \
  --lock plans/package/plan.lock.json \
  --operation-id managed-step-1 \
  --expected-revision 1 \
  --source-revision <git-sha> \
  --out work/run/managed-step-1.json
```

`--lock` можно не указывать, если `plan.lock.json` лежит рядом с manifest.

## Подтверждение

Команда возвращает `agent-managed-lifecycle-runner-receipt.v1`.

Важные поля:

- `status`: `PASS`, если связь плана и состояния актуальна; `FAIL`, если
  выполнение нужно остановить.
- `nextAction`: `agent-managed-lifecycle-next-action.v1`, короткое описание
  следующего действия для хоста.
- `modelCallsStarted: false`: команда не запускает модель.
- `stateWritten: false`: команда не меняет сохранённое состояние.
- `hostLaunchStarted: false`: реальные запуски остаются ответственностью
  адаптера или хоста.
- `blockers`: причины закрытого отказа, например устаревшая ревизия состояния,
  незафиксированный план, несовпадение lock-файла, исходной ревизии или
  отсутствие обязательного отчёта аудита реализации.

## Граница с `runner`

`workflow run` не заменяет `agent-lifecycle runner
start/status/transition/stop/resume`. Существующий runner управляет
ограниченным состоянием выполнения. Управляемый шаг жизненного цикла только
показывает следующий шаг из уже сохранённого состояния и зафиксированного
контракта плана.

## Проверка отсутствия модельных вызовов

Релизная проверка сканирует модули управляемого шага через
`tools/release/validate_no_model_calls.py`. Проверка отклоняет прямые импорты
клиентов моделей или сети, например `openai`, `anthropic`, `requests`, `httpx`
и `urllib`.

## Обычный цикл хоста

1. Вызвать `workflow run`.
2. Если `status` равен `FAIL`, показать структурированную причину остановки.
3. Если `nextAction.type` равен `launch-tasks`, хост запускает указанные
   пакеты задач и позже записывает `workflow task-result`.
4. Если план требует аудит реализации, запустить `agent-lifecycle audit
   implementation` и передать принятый отчёт в `workflow task-accept`.
5. Если `nextAction.type` равен `run-final-audit`, запускается независимая
   финальная проверка.
6. Если `nextAction.type` равен `finalize-run`, вызывается `workflow finalize`
   с принятым финальным аудитом и путём для итогового доказательства.

Цикл остаётся детерминированным: каждое изменение состояния по-прежнему идёт
через существующие команды переходов с `operation-id`, `expected-revision` и
`source-revision`.
