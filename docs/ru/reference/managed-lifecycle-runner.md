# Управляемый шаг жизненного цикла

`agent-lifecycle workflow run` - ограниченная команда чтения над сохранённым
состоянием жизненного цикла. Она не запускает модель, не запускает процесс
хоста и не меняет состояние. Команда проверяет связь текущего состояния с
зафиксированным планом и возвращает следующий шаг, который должен выполнить
хост.

Перед передачей пакета управляемому runner используйте [проверку целостности
плана](plan-verification.md). Она проверяет канонический манифест, пути
полномочий, трассируемость, lock-файл и состав пакета, не выполняя ни одной
команды из плана. Успешная проверка является предусловием целостности пакета,
но не заменяет аудит реализации и решение о выпуске.

Это закрывает разрыв между процедурой в skill и CLI: хост может спросить ALK,
что делать дальше, не восстанавливая процесс из текста чата.

## Необязательный контроль жизненного цикла

Релиз 1.84 не меняет полномочия управляемого шага. Необязательный контроль
адаптера может добавить подтверждения до действия, после действия и при
остановке вокруг действия из `nextAction`, но сам шаг по-прежнему выводит его
из зафиксированного плана, lock-файла, состояния и принятых подтверждений.
Промпт плагина или объявление адаптера не могут заменить эти источники. Сейчас
комплектные адаптеры публикуют `GUIDANCE_ONLY` и `NO_RECOMMENDATION`; уровень
`ENFORCED` возможен только для производителя хоста с точной версией и
отрицательными подтверждениями.

## Команда

```bash
agent-lifecycle workflow run \
  --state run.state.json \
  --manifest plans/package/plan.manifest.json \
  --lock plans/package/plan.lock.json \
  --operation-id managed-step-1 \
  --expected-revision 1 \
  --source-revision <git-sha> \
  --progress-hook stderr \
  --out work/run/managed-step-1.json
```

`--lock` можно не указывать, если `plan.lock.json` лежит рядом с manifest.

## Подтверждение

Команда возвращает `agent-managed-lifecycle-runner-receipt.v1`.

Важные поля:

- `status`: `PASS`, если связь плана и состояния актуальна; `FAIL`, если
  выполнение нужно остановить.
- `nextAction`: `agent-managed-lifecycle-next-action.v1`, короткое описание
  следующего действия для хоста.
- `modelCallsStarted: false`: команда не запускает модель.
- `stateWritten: false`: команда не меняет сохранённое состояние.
- `hostLaunchStarted: false`: реальные запуски остаются ответственностью
  адаптера или хоста.
- `blockers`: причины закрытого отказа, например устаревшая ревизия состояния,
  незафиксированный план, несовпадение lock-файла, исходной ревизии или
  отсутствие обязательного отчёта аудита реализации.

## Граница с `runner`

`workflow run` является каноническим представлением следующего шага. Команды
`agent-lifecycle runner start/status/transition/stop/resume` пока остаются
только устаревшим совместимым журналом для исторических интеграций. Они не
пишут состояние workflow, не выдают полномочия, не принимают задачу и не
финализируют запуск. В их подтверждениях указано `journalOnly: true` и
приведён соответствующий переход `workflow`. Новые интеграции должны сразу
использовать команды workflow.

Политика runner проверяется относительно замороженных бюджетов workflow на
попытки, перенаправления, разделения, токены и время. Отсутствие полномочий
или более широкий лимит блокирует совместимую команду; runner не может сам
создать эти полномочия.

## Общий словарь действий

Workflow, управляемый runner, контроль хоста и совместимый CLI используют
закрытый `agent-lifecycle-action-catalog.v1`. Он статичен и не настраивается
профилем проекта. Проверка
`tools/release/validate_workflow_transition_contract.py` не позволяет новой
фазе, вердикту или команде стать достижимыми без объявленного действия.

## Проверка отсутствия модельных вызовов

Релизная проверка сканирует модули управляемого шага через
`tools/release/validate_no_model_calls.py`. Проверка отклоняет прямые импорты
клиентов моделей или сети, например `openai`, `anthropic`, `requests`, `httpx`
и `urllib`.

## Обычный цикл хоста

1. Вызвать `workflow run`.
2. Для управляемых команд добавить `--progress-hook stderr`, чтобы увидеть
   прогресс в терминале, или `--progress-hook receipt --progress-receipt
   <path>`, чтобы сохранить структурированное подтверждение. Для отдельного
   терминала можно вызвать `report progress --terminal`, `report progress
   --watch` или `report progress-bridge`.
3. Если `status` равен `FAIL`, показать структурированную причину остановки.
4. Если `nextAction.type` равен `launch-tasks`, хост запускает указанные
   пакеты задач и позже записывает `workflow task-result`.
5. Если следующий шаг имеет тип `accept-task`, провести независимую проверку
   и вызвать `workflow task-review-apply` (или совместимую обёртку
   `task-accept`) с точными ревизиями состояния и источника.
6. Если независимая проверка вернула `REWORK`, использовать тот же
   канонический маршрут с идентификаторами открытых находок. Только эта задача
   переходит в `REWORK`, запуск остаётся в `RUNNING`, а следующий шаг снова
   возвращает её в `launch-tasks`. `task-start` открывает следующую свободную
   ограниченную попытку.
7. Если запуск требует одобрения, принять точное подтверждение командой
   `workflow authorize`; при внешнем действии использовать
   `external-pause`/`external-resume` с соответствующим подтверждением.
8. Если `nextAction.type` равен `run-final-audit`, выполнить независимый
   финальный аудит и применить его через `workflow final-audit-outcome`. Только
   `ACCEPTED` продолжает финализацию; остальные исходы выбирают свой
   типизированный маршрут восстановления.
9. Если `nextAction.type` равен `finalize-run`, вызвать `workflow finalize` с
   принятым финальным аудитом и путём для итогового доказательства.

Цикл остаётся детерминированным: каждое изменение состояния по-прежнему идёт
через существующие команды переходов с `operation-id`, `expected-revision` и
`source-revision`.

Отображение прогресса не входит в путь изменения состояния. Оно читает
состояние жизненного цикла, подтверждённые хостом артефакты использования и
необязательный счётчик изменений. Поэтому его можно показывать в Codex, Claude
Code, OpenCode или другом хосте без добавления этих строк в запрос к модели.

Установка plugin или skill не доказывает, что задача прошла жизненный цикл.
`AUTO` для прогресса требует управляемой команды ALK или поставляемой обёртки
адаптера, которая записывает подтверждение управляемого рабочего цикла.
