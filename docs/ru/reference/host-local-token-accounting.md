# Локальный учёт токенов хоста

## Обслуживание закрытых запусков

Команда `alk workflow maintenance --authority /absolute/private/maintenance-authority.json
--authority-sha <sha256> --candidate-limit 32 --deadline <UTC>` вызывает
существующую очистку журнала. Сырые подробности становятся доступными для
удаления через 30 дней после полного финансового закрытия. Незавершённые
запуски и финансовые исключения сохраняют подробности. Итоги расходов,
защита от повторного списания и записи закрытия не удаляются.

Приватный корень определяется родителем канонического файла полномочий;
журнал, идентичности файлов, замороженный manifest/lock и digest автора
закреплены в этом файле. Соседний `maintenance-authority.json.writer.json`
содержит ровно `ref` и `digest` исходного автора журнала. Digest этого
канонического объекта должен совпадать с `writerDigest`. Этот файл сохраняется
после очистки SQL: исходной записи автора среди подробностей уже может не быть.
Оба файла принадлежат текущему пользователю и имеют права 0600 в каталоге 0700.
Переопределение журнала или приватного корня запрещено.

Команда использует реальные UTC, исходный deadline и максимум 60 секунд работы.
В результате есть хеши идентификаторов запусков, состояния PENDING/OVERDUE и
следующая дата очистки; текст запросов и ответов не выводится. Неподдерживаемые
безопасные операции с файлами вызывают отказ до удаления. При PARTIAL
обязательства сохраняются для следующего запуска по расписанию. COMPLETE
означает завершение ограниченной команды; установка расписания, проверка на
целевой ОС и полные гарантии финансового учёта подтверждаются отдельно.

ALK не переносит телеметрию конкретных моделей и поставщиков в общее ядро.
Адаптер может объявить локальный нормализатор расхода: он читает один
ограниченный артефакт хоста и формирует существующее подтверждение
`agent-lifecycle-model-usage-receipt.v1`. Дескриптор использует контракт
`adapter-local-usage-normalizer.v1`.

Так разделяются две ответственности:

- нормализатор адаптера определяет, какие счётчики действительно сообщил хост;
- ядро проверяет происхождение, привязку к маршруту, ограничения расхода и
  допустимость этих данных для S1/S2.

## Уровни подтверждения

| Состояние | Значение | Допустимо для S1/S2 |
| --- | --- | --- |
| `UNSUPPORTED` | Локальный нормализатор не объявлен. Ядро может показать консервативную оценку. | Нет |
| `FIXTURE_ONLY` | Разбор проверен на ограниченных тестовых образцах, но не подтверждён для диапазона версий реального хоста. | Нет |
| `QUALIFIED` | Для нормализатора указан диапазон версий хоста и принято независимое подтверждение. | Да, только при `source: host` и `status: ATTESTED` |

Уровень поддержки адаптера и состояние нормализатора токенов не связаны
автоматически.
Например, Qwen Code остаётся адаптером `VERIFIED`, но вынесенный нормализатор
пока имеет состояние `FIXTURE_ONLY`. Ранее принятое подтверждение жизненного
цикла не считается доказательством для нового контракта разбора.

## Привязка подтверждения

Адаптер вкладывает подтверждение использования модели в результат операции
хоста. Схема `agent-host-operation-receipt.v1` при этом не меняется.
Сопутствующее подтверждение связывает:

- операцию и отпечаток решения о маршруте;
- адаптер и хост;
- нейтральный класс модели и отпечаток локальной настройки модели;
- SHA-256, размер и формат исходного артефакта без локального пути;
- состояние нормализатора и отпечаток его исходного файла.

Исходный JSONL, запросы, ответы, секреты и локальные пути в переносимое
подтверждение не копируются. Идентификатор сеанса сохраняется только тогда,
когда соответствует ограниченному формату непрозрачного идентификатора.

## Поддерживаемые нормализаторы

| Адаптер | Артефакт | Состояние нормализатора |
| --- | --- | --- |
| Gemini CLI | `stream-json` | `FIXTURE_ONLY` |
| Kimi Code | `stream-json` | `FIXTURE_ONLY` |
| Qwen Code | `stream-json` | `FIXTURE_ONLY` |
| Остальные встроенные адаптеры | Контракт не объявлен | `UNSUPPORTED` |

Все три нормализатора находятся в
`adapters/<adapter>/usage_normalizer.py`. Исполнитель адаптера и испытательный
стенд загружают один и тот же файл через защищённый загрузчик. Он отклоняет
выход за каталог адаптера, символьные ссылки и несовпадение пути с
дескриптором.

Проверить объявления и границы разбора:

```bash
python tools/release/validate_host_usage_normalizers.py \
  --adapter-root adapters \
  --evidence work/validation/host-usage-normalizers.json

agent-lifecycle adapter validate \
  --descriptor adapters/qwen-code/adapter.descriptor.json
```

Проверить подтверждённый расход по маршруту и ограничениям:

```bash
agent-lifecycle model usage-check \
  --receipt work/run/model-usage.json \
  --route-decision work/run/model-route.json \
  --budget-targets conformance/core/budget-targets.v1.json
```

Числа из тестового образца точны для этого образца, но для гейтов жизненного
цикла они остаются данными `ESTIMATED`. Одна метка состояния не может повысить
их до подтверждения реального хоста.

## Консервативная оценка

Если точных данных хоста нет, ядро использует заметную верхнюю оценку: один токен на каждый байт
исходного артефакта. Она помечается как
`source: core-estimate`, `status: ESTIMATED`. Агрегатор считает данные
подтверждёнными только при одновременном наличии `source: host` и
`status: ATTESTED`.

Учёт токенов остаётся учётом ресурсов, а не цены. Хост может сообщить денежные
метаданные, но ALK не содержит канонического каталога тарифов поставщиков.

### Проверка входов профилей учёта

`profiles/accounting-adapter-capabilities.v1.json` содержит замороженные ожидания
для всех 12 адаптеров. Записи `EXPECTED_NOT_OBSERVED` сохраняют кандидатов,
источники и пределы утверждений; это не принятые профили установленных хостов.
Сохранённые снимки под `work/` нужны для воспроизводимой проверки релиза.

Из релизного checkout, с поддерживаемой версией Python:

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 tools/release/validate_accounting_adapter_profiles.py \
  --manifest tasks/release-2-16/plan.manifest.json --catalog-only \
  --evidence work/release-2-16/accounting-catalog-preflight.json
```

Вместо `--catalog-only` можно задать `--preflight --profiles-root <корень-доказательств>`:
проверяются оболочки выбранных профилей, привязки ожидания/версии/маршрутов/кейсов,
пределы утверждений и ограниченный граф файловых ссылок. Отсутствующие или неверные
входы, symlink, выход за корень, изменённые байты, конфликт ссылок, повторные ключи
JSON и недоступное безопасное чтение вызывают отказ. Выходной файл создаётся один
раз, существующий не перезаписывается.

Отчёт `alk-accounting-profile-preflight.v1` может получить лишь
`STRUCTURE_VALID_ONLY`. При проверке выбранных профилей команда возвращает код 2
даже с корректными входами: происхождение наблюдений, независимость проверки,
квалификация и фактический отказ до отправки требуют отдельных доказательств.
Входные метки PASS/ACCEPTED не дают права на запуск или финансовой гарантии.
Диагностика не заменяет EV216-ACCOUNTING-ENFORCEMENT и завершённый
P-FINAL-VALIDATOR. Частичный учёт не закрывает расходы запуска и не разрешает
30-дневную очистку подробностей.

## Отказ в запросе гарантий перед запуском

Явный `accountingCapabilityRequest` в advisory планирования или risk-входе управляемого запуска получает отказ до запуска процесса, пока не доступны окончательная квалификация профиля и подключение к запуску. Отказ распространяется на null, некорректный запрос и переданный результат `PASS` или `ALLOW_CAPABILITY`. Запуск без такого запроса сохраняет действующие lifecycle-проверки и не заявляет финансовых гарантий.

`alk host-launch preflight --profile <local-launch-profile> --accounting-request <request.json>` отказывает до проверки версии исполняемого файла. `alk host-launch accounting-check --profile <accounting-profile.json> --request <request.json> --expectation-digest <sha256> --plan-digest <sha256> --candidate-digest <sha256> [--out <new-file>]` возвращает точное структурное несовпадение либо неподтверждённые доказательства и код выхода 2. Профиль — закрытый envelope `alk-accounting-profile.v1`. Результат является диагностикой отказа, не принимающей квитанцией и не разрешением запуска. Окончательная квалификация адаптеров и проверка текущих доказательств остаются обязательными.

## Промежуточная квалификация по исходным материалам

`alk host-launch qualification-check --profiles-root <корень-доказательств> --adapter <адаптер> --request <request.json> [--out <новый-файл>]` проверяет промежуточные `profile-payload.json` и `qualification.json` в каталоге адаптера. Привязки вычисляются по замороженным входам релиза и текущим Python-исходникам ALK. Проверяются архивные байты источников и решения по возможностям; после проверки реально опубликованной обычной AREA-рецензии материалы читаются повторно в пределах общего лимита. Небезопасные или изменённые входы получают отказ. Рецензия должна покрывать точную проекцию содержимого `qualification-subject.json` и обязательство адаптера. Проекция исключает ссылку на рецензию, чтобы избежать цикла хешей.

`ALLOW_CAPABILITY` доступен только для профиля `LIFECYCLE_ONLY` по исходным материалам без утверждений о гарантиях. Отсутствие публикации, переданные метки PASS, нерешённые возможности, положительные native-наблюдения и более сильные финансовые запросы дают отказ и код выхода 2. `dispatchEntitlement` всегда false: результат не принимает окончательный профиль, не разрешает запуск, закрытие расходов или очистку и не выпускает итоговую квитанцию релиза. Защита запуска сохраняется. Синтетический тест с заменой проверки происхождения доказывает проверку связей, не совместимость адаптера и не опубликованную квалификацию.

Итоговый валидатор вызывается с `--profiles-root` без `--preflight`. Требуются окончательные оболочки профилей, квалификация и доказательства resolver, реально опубликованные обычные рецензии обеих проекций и сырых трасс счётчика, а также существующая проверка квитанции core с текущим subject. Чтение профилей имеет общий лимит. При отказе создаётся `.diagnostic.json`, принимающая квитанция отсутствует. После21 успешной проверки подготовленный результат WS216-02 нужен для выпуска типизированной DECLARED-квитанции EV216-ACCOUNTING-ENFORCEMENT; приёмка workflow и аудитором выполняется отдельно. Наличие реализации не доказывает квалификацию адаптеров или готовность релиза.

Трасса resolver сохраняет точные входы отсутствующей, устаревшей, поддельной и повторно переданной квалификации как строки JSON; producer должен выполнить их, а не только подписать четыре запроса. Каждая из девяти общих проверок указывает проверенные условия или сохранённые свидетели core. Перед выдачей квитанции повторно сверяются байты входов, происхождение рецензий, исходный срок задачи и полное утверждение о текущем наборе изменений. 21 случай профилей составляет одно DECLARED-наблюдение команды; замороженная квитанция enforcement требует 85 случаев пяти команд, поэтому одного наблюдения недостаточно для приёмки задачи.
