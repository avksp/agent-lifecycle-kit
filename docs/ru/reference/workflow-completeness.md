# Полнота workflow

Release 2.17 развивает существующие state, журнал событий и checkpoints.
Локальные гарантии не подтверждают защищённость хоста и не измеряют все
модельные вызовы. Недоступный расход хоста остаётся неизвестным, а не нулевым.

## Последовательная запись и ограничения чтения

Изменяющая workflow операция получает блокировку ОС до чтения state и
удерживает её до завершения commit. Проверки ожидаемой ревизии и уникальности
operation ID выполняются внутри этой границы. Конкурирующий процесс обязан
использовать наблюдаемую `--expected-revision`; незаметно повторно использовать
ревизию нельзя. Пустые закрытые файлы блокировки хранятся в пользовательском
`~/.agent-lifecycle-kit/workflow-locks/`, вне проекта и снимков исходников.
Имена — хеши канонического пути state; варианты регистра и Unicode используют
одну блокировку. Файл сохраняется после освобождения. Его наличие
не означает удержание блокировки; возраст файла не разрешает её перехват.
Ожидание ограничено; завершение процесса освобождает блокировку ОС.

Ядро заранее готовит полные следующие state, operation record, событие и
метаданные checkpoint. Лишь после проверки начинается запись артефактов.
Действуют существующие пределы JSON: 1 048 576 байт и вложенность 128.
Ошибки `json-input-too-large` и `json-input-depth-exceeded` сохраняют читаемое
состояние и историю. Журнал не обрезается, накопленный расход не обнуляется.

Сначала дописывается событие, затем заменяется state. Сбой между этими шагами
может оставить журнал впереди state. Следующая операция отказывает с
`workflow-split-brain`, не приписывая себе успешный commit. Повторные или
неупорядоченные ревизии событий и повторные operation ID недопустимы.
Старые строки без schema/operation metadata остаются читаемыми; уникальность
ID проверяется там, где ID присутствует. Отсутствие старых метаданных
не подтверждает полноту учёта.
Это не транзакция базы данных с откатом всех файлов: сбой после подготовки
может оставить неизменяемые доказательства. Сохраните их для восстановления;
не удаляйте события и не используйте operation ID повторно.

## Незавершённые пункты

Исходы пунктов `INCOMPLETE`, `BLOCKED`, `NOT_STARTED` и `DEFERRED` допустимы
для непринимающего результата. Они не дают принять задачу. `plannedItemId`
сохраняется между попытками. Следующий результат обязан включать каждый ранее
незавершённый пункт; иначе возникает `task-result-unresolved-item-omitted`.

Перевод такого пункта в `COMPLETE` требует доказательства от успешных команд,
выбранных в текущем результате. При его отсутствии возникает
`task-result-item-resolution-unproven`. Артефакты старых попыток неизменяемы.
Изменение объёма проходит существующий независимый review и принятие нового
плана. Удаление или переименование пункта работником не разрешает исключение.
Проверяются также результаты из `priorSnapshots`, сохранённые при adoption.
Для исключения незавершённых ID старый независимый review `CONTRACT_CHANGE`
должен явно перечислить `contractChangeRequest.excludedPlannedItemIds`.
Штатно сохранённый запрос обязан совпадать с этим неизменяемым review; нужен
фактически принятый более новый план. Обычное adoption и запрос работника
не разрешают потерять пункт.

## Явное подтверждение предпосылок

`dependsOn` описывает зависимости пакета, но не доказывает принятие или выпуск
предшественника. Для обязательной локальной проверки используется закрытое
расширение `extensions.prerequisiteAcceptance` с полями `required` и
`dependencies`. Каждая запись содержит только `packageId`, `sourceRevision`,
`evidencePath` и SHA256 точных байтов файла в `sha256`.

При `required: true` доказательства должны покрывать объявленные зависимости,
совпадать по пакету, исходной ревизии и хешу и содержать независимое заключение
`ACCEPTED`. Переданные записи проверяются также при `required: false`.
Самостоятельный пакет без зависимостей допустим. Ошибки
`prerequisite-acceptance-*` блокируют adoption; ALK не скачивает и не создаёт
недостающие доказательства. Принятие не подтверждает публикацию или аттестацию
хоста. Пример JSON приведён в английской версии этого документа.

## Техническое прерывание ревью

Отсутствующий или обрезанный ответ — техническое прерывание, а не независимый
вердикт `REWORK`. Для уже сохранённого результата, ожидающего проверки,
используется существующая блокировка запуска:

```sh
agent-lifecycle workflow block --state run.state.json --operation-id review-wait \
  --expected-revision 12 --blocker-code review-response-missing \
  --review-task WS-01 --reason 'Ответ проверяющего не доставлен'
agent-lifecycle workflow resolve --state run.state.json --operation-id review-resume \
  --expected-revision 13 --reason 'Продолжить проверку того же результата'
```

Второй технический код — `review-response-truncated`. Блокировка связывается
с задачей, попыткой, результатом, packet, планом, исходной ревизией, findings,
бюджетами и исходными сроками. Восстановление требует действующих полномочий,
остатка объявленного бюджета, неизменного предмета и неистёкших абсолютных
сроков. Расход может увеличиваться, но не уменьшаться или терять историю.
Сохраняется та же попытка. Восстановление не создаёт фиктивного review и
не закрывает смысловые замечания. Причину отказа поясняют коды
`review-interruption-*` и `review-recovery-*`.

Этот путь не запускает запрос провайдеру, не выдаёт попытку, не увеличивает
лимит и не продлевает срок. Политика повторов провайдера здесь не реализована.
Отдельные внешние действия используют существующие внешние receipts.

## Архитектурные цели и совместимость

Целевые размеры файла и функции дают явные предупреждения. Жёсткие лимиты
файла, функции и количества объявлений верхнего уровня остаются блокирующими.
Превышение цели функции имеет код `architecture-function-target-exceeded`.
Проверка declared-limit semantics проверяет согласованность классификации
и диагностики отчёта, а не текущие исходники. Её успех не отменяет провал
самой архитектурной проверки.

Корректные state и история 2.16 остаются доступны для чтения. Новый исполняемый
план требует явно указанного tier и полного набора его integrity-входов.
Дополните входы и получите review/freeze; не понижайте tier и не правьте
замороженные полномочия ради прохождения проверки. Для технического
восстановления версии 4 состояние версии 3 сначала проходит штатную миграцию.
