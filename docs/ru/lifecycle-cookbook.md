# Практические сценарии жизненного цикла

Используйте этот документ, когда понятен тип работы, но не хочется вручную
собирать низкоуровневые команды ALK. Все сценарии сохраняют входные данные в
черновом статусе, пока проверенный план или зафиксированный запрос запуска не
разрешит выполнение.

## Как выбрать сценарий

| Нужно | Сценарий | Останавливается до реализации |
| --- | --- | --- |
| Исследовать область и составить план | [Исследование и планирование](#исследование-и-планирование) | Да |
| Проверить один файл задачи | [Проверка одного Markdown-файла](#проверка-одного-markdown-файла) | Да |
| Проверить несколько файлов плана | [Проверка папки с Markdown-планом](#проверка-папки-с-markdown-планом) | Да |
| Проверить код, PR или MR | [Проверка изменений кода](#проверка-изменений-кода) | Да |
| Проверить готовую реализацию ALK | [Аудит подтверждений реализации](#аудит-подтверждений-реализации) | Нет, проверяет уже выполненную работу |
| Подключить нескольких проверяющих | [Согласованная перепроверка](#согласованная-перепроверка) | Да, если зафиксированный план не требует кворум |

## Исследование и планирование

Используйте этот путь, когда результатом должен быть анализ, архитектурная
записка или план.

```bash
cat > work/tasks/research.md <<'EOF'
# Задача

Исследуй текущий процесс сессий адаптеров и составь план улучшения.
Код не менять.

Верни:
- наблюдения по архитектуре;
- риски и открытые вопросы;
- рекомендуемую форму плана ALK;
- команды проверки, которые понадобятся позже.
EOF

agent-lifecycle adapter task start \
  --adapter codex \
  --file work/tasks/research.md \
  --out work/tasks/research-intake.json

agent-lifecycle review-mesh recommend \
  --intake work/tasks/research-intake.json \
  --out work/tasks/research-recommendation.json
```

Остановитесь здесь, если нужна только аналитика. Для реализации позже
превратите принятый план в обычный пакет ALK и зафиксируйте его.

## Проверка одного Markdown-файла

Подходит для задачи, предложения или плана в одном файле:

```bash
agent-lifecycle adapter task start \
  --adapter claude \
  --file tasks/proposal.md \
  --out work/review/proposal-intake.json

agent-lifecycle review-mesh recommend \
  --intake work/review/proposal-intake.json \
  --out work/review/proposal-recommendation.json
```

Идентификатор адаптера выбирает локальный контекст хоста для подтверждения
приёма задачи. Он не запускает хост или модель для обычного Markdown-входа.

## Проверка папки с Markdown-планом

Если план разложен по нескольким Markdown-файлам, используйте импорт:

```bash
agent-lifecycle import plan \
  --source tasks/release-1-40/ \
  --dialect spec-kit \
  --out work/review/plan-import.json
```

Затем создайте одну задачу проверки, которая ссылается на папку или на
полученное подтверждение импорта:

```bash
cat > work/review/plan-review-task.md <<'EOF'
# Задача

Проверь Markdown-пакет плана из work/review/plan-import.json.
Реализацию не начинать.

Проверить требования, критерии приёмки, маршруты подтверждений, владение
файлами, проверки безопасности и релизные заявления.
EOF

agent-lifecycle adapter task start \
  --adapter codex \
  --file work/review/plan-review-task.md \
  --out work/review/plan-review-intake.json
```

## Проверка изменений кода

Подготовьте файл изменений через Git, GitHub CLI или refspec GitLab, затем
передайте в ALK одну явную задачу проверки:

```bash
mkdir -p work/code-review/current
git diff origin/main...HEAD > work/code-review/current/diff.patch
```

```bash
agent-lifecycle adapter task start \
  --adapter codex \
  --file work/code-review/current/review-task.md \
  --out work/code-review/current/intake.json
```

Если архитектура описана, перечислите документы архитектуры в файле задачи.
Если архитектура не описана, попросите сначала восстановить ответственность
модулей и только затем проверить файл изменений относительно этой картины.

Подробные примеры: [Сценарии проверки кода](code-review-workflows.md).

## Аудит подтверждений реализации

Используйте аудит реализации после того, как исполнитель подготовил результат
задачи и независимую проверку:

```bash
agent-lifecycle audit implementation \
  --manifest tasks/release-x/plan.manifest.json \
  --state work/run.state.json \
  --task WS-01 \
  --result work/WS-01/attempt-1/task-result.json \
  --review work/WS-01/attempt-1/task-review.json \
  --out work/WS-01/attempt-1/implementation-audit.json
```

Добавляйте `--review-mesh-quorum <path>` только тогда, когда зафиксированный
план требует кворум для этого этапа.

## Согласованная перепроверка

Для рискованных исследований, планов или аудитов создайте назначения через
`review-mesh assign`, запустите проверяющих вне ALK, импортируйте их JSON-вывод,
затем объедините выводы и проверьте кворум.

Конкретные примеры Codex, Claude и OpenCode/GLM есть в
[практических сценариях групповой проверки](review-mesh-workflow.md). GLM здесь
только пример модели за OpenCode; можно использовать любую настроенную модель,
изменив команду конкретного CLI.

## Правила безопасности

- Не помещайте секреты и приватные значения окружения в файлы задач.
- В переносимых пакетах используйте относительные пути репозитория.
- Считайте `review-mesh recommend` советом, пока зафиксированный план явно не
  включил этот режим.
- Установка плагина сама по себе не доказывает, что жизненный цикл ALK был
  выполнен.
- Обычный текст, Markdown и импортированные планы сами по себе не разрешают
  реализацию.
