# Проверки качества Python и участие в разработке

В релизе 1.77 существующая дисциплина разработки Python стала воспроизводимой.
Инструменты качества используются только при разработке и не становятся
зависимостями ALK во время выполнения.

## Подготовка окружения

Перед проверками установите зафиксированную группу инструментов:

```bash
uv sync --locked --group quality
```

В группе зафиксированы Ruff, mypy и coverage. Пакет сохраняет отсутствие
зависимостей во время выполнения.

## Локальные проверки

Запустите отдельные инструменты и полный реестр тестов:

```bash
uv run --frozen --group quality ruff check src/agent_lifecycle
uv run --frozen --group quality ruff format --check src/agent_lifecycle
uv run --frozen --group quality mypy src/agent_lifecycle
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 -m unittest discover -s tests -t . -q
```

Производитель релизных подтверждений запускает те же зафиксированные
инструменты с ограничениями времени, вывода и процессов:

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src uv run --frozen --group quality \
  python3 tools/release/run_python_quality.py \
  --policy policy/python-quality.json \
  --package-root src/agent_lifecycle \
  --tests-root tests \
  --test-top-level . \
  --base-sha <base-commit> \
  --work-root work/quality-raw \
  --evidence work/python-quality-run.json
```

Сформированные подтверждения проверяются командой
`tools/release/validate_python_quality.py`. Проверяются корректность кода,
форматирование, миграционные предупреждения, длина строк, mypy, полный поиск
тестов через unittest и покрытие.

## Как работает ограничитель долга

Политика хранит старые находки с привязкой к пути, правилу и отпечатку
исходного файла. Наличие старой находки не разрешает добавлять новую: проверка
блокируется при новой находке, росте счётчика или изменении отпечатка. Каждый
изменённый релизом файл должен выйти из списка корректностных находок. Порог
покрытия строк 76% и точная базовая линия предшествующего окружения не могут
понижаться ради успешного релиза.

Нельзя отключать проверку безопасности, архитектуры или качества ради обхода
ошибки. Нужно исправить находку, обновить проверенный план и подтверждения либо
остановиться со статусом `REVIEW_REQUIRED`.

## Стабильные ошибки CLI и встроенные ресурсы

Корневой CLI возвращает `agent-lifecycle-error.v1` с кодом выхода `2` для
ожидаемых ошибок ввода-вывода, декодирования, глубины JSON и непредвиденных
ошибок. Сообщение очищается и не содержит трассировку или локальный абсолютный
путь. Поведение библиотечных исключений и `KeyboardInterrupt`/`SystemExit` не
меняется. Подробности приведены в [контракте ошибок CLI](../reference/cli-errors.md).

Встроенные профили загружаются как ресурсы пакета. Поэтому установленный wheel
работает вне исходного дерева, а одноимённый файл в текущей папке не может
подменить встроенный профиль. Явно переданный путь к профилю сохраняет
приоритет. Поддерживаемая поверхность импорта описана в [контракте API
Python](../reference/python-api.md); внутренние модули, которых там нет, не
являются обещанием совместимости.

## Перед отправкой изменения

1. Оставьте изменения внутри проверенного набора файлов.
2. Запустите целевые тесты затронутого поведения.
3. Запустите полный unittest и проверки качества.
4. Проверьте JSON-подтверждения и документацию на обоих языках.
5. Укажите команды, точные ревизии и оставшиеся блокеры.

Процесс релиза остаётся источником полномочий для области изменений,
подтверждений, независимого ревью и итоговой приёмки.

## Единая архитектурная политика

Числа берутся из `policy/architecture-limits.json`; таблица проверяется тестом.
Целевые значения — предупреждения, жёсткие — блокирующие пределы.

| Policy key | Limit |
| --- | ---: |
| `targetFileLines` | 800 |
| `hardFileLines` | 1200 |
| `targetFunctionLines` | 80 |
| `hardFunctionLines` | 150 |
| `hardSymbols` | 80 |
| `cliTargetFunctionLines` | 80 |
| `cliHardFunctionLines` | 150 |

```bash
PYTHONPATH=src python3 tools/release/validate_architecture_complexity.py \
  --package-root src/agent_lifecycle --policy policy/architecture-limits.json \
  --evidence work/architecture-complexity.json
PYTHONPATH=src python3 tools/release/validate_module_dependencies.py \
  --package-root src/agent_lifecycle --policy policy/architecture-dependencies.json \
  --require-acyclic-modules --require-acyclic-packages \
  --evidence work/module-dependencies.json
```

Mypy baseline пуст: любая новая ошибка source-wide mypy блокирует приёмку.
Прежний lint/format baseline не расширяется, порог покрытия 76% не снижается.
Полный локальный unittest запускается один раз для неизменного кандидата;
quality runner повторяет discovery для собственных coverage-доказательств в CI.
Повтор успешной локальной проверки требует изменения её зависимостей.

## Области проверок Python

`policy/python-quality.json` задаёт каждый набор проверяемых файлов. Для
пакета действует существующий ограничитель долга. Файлы из `tooling.paths`,
включая запускатель проверок, проходят все выбранные правила Ruff,
форматирование и строгий mypy без baseline долга. Файлы из `tests.paths`
проходят проверки корректности E4/E7/E9/F/B. Остальные тесты продолжают
выполняться в обязательном наборе тестов.

Валидатор связывает байты выбранных тестов и аргументы команд с подтверждением.
Он отклоняет некорректную revision, ослабленный набор правил, необъявленные
тестовые пути в tooling или strict и тестовые записи в baseline Ruff или mypy.
Корректные прежние policy без выбранной области тестов сохраняют прежнюю
трактовку. Успешная валидация означает соответствие проверенных областей policy;
остаточный долг виден в сводке диагностики. Полный quality runner уже запускает
unittest для измерения покрытия, поэтому один полный локальный запуск может
закрыть обе проверки для одинаковых исходников и входов.

## CI для pull request и main

Pull request запускает все 25 платформенных, foundation и Python quality
ячеек из `.github/workflows/ci.yml`. Имена обязательных проверок и отдельный
workflow CodeQL сохраняются. Каждая ячейка фиксирует проверенный коммит и
дерево, discovery тестов, попытку запуска, образ runner, интерпретатор и
закреплённые инструменты. Для подготовки окружения CI использует закреплённую
версию uv для своей роли и проверяет хеши build-зависимостей из
`tools/ci/build-requirements.txt`.

При push в main CI может подтвердить одну полную успешную попытку слитого
pull request из того же репозитория. Все 25 текущих ячеек должны подтвердить
совпадение исходников и окружения. Пять quality probes заново выполняют
статические проверки, strict mypy и валидацию качества по байтам
квалифицированного coverage JSON. К этим байтам применяются прежние пороги.

Если все probes успешны, main выбирает `QUALIFIED_REUSE` для всей матрицы.
При отсутствии, устаревании или несовпадении доказательств режим `FULL`
выполняет все 25 наборов тестов на main. Ошибка текущей статической проверки
или повреждение внутреннего доказательства останавливает квалификацию.
В обоих режимах заново выполняются проверки истории, интеграции, пакетов и
CodeQL. Итоговый отчёт фиксирует режим и фактически запущенные наборы тестов.

## Подготовка данных для тестов репозитория

Полные тесты репозитория используют встроенную релизную фикстуру. Перед полным
запуском восстановите её в чистой копии той же командой, что выполняет CI:

```bash
python -m zipfile -e fixtures/release-2-16-tests.zip tasks/release-2-16
```

Команда записывает файлы в `tasks/release-2-16`. Если каталог содержит прежние
планы, используйте отдельный чистый worktree. Восстановление фикстуры и полный
quality-запуск выполняйте в этом worktree, чтобы сохранить планы и доказательства.
