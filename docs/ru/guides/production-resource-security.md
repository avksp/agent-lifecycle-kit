# Ресурсы и безопасность в рабочих запусках

ALK должен помогать довести задачу до результата с подтверждениями, а не
тратить основную часть запуска на доказательство собственного процесса.
Выбирайте самый лёгкий режим жизненного цикла, который соответствует риску
задачи.

## Режим ресурса

- `light`: небольшие и низкорисковые правки с узкой областью владения.
- `standard`: обычные задачи по исправлению ошибок и доработке функций.
- `strict`: безопасность, риск потери данных, совместимость публичного API или
  сложная независимая проверка.
- `release`: изменения метаданных пакета, заметок релиза, тегов или
  публикационных артефактов.

Любой режим может использовать компактные артефакты контекста, отчёты об
использовании модели и ограничения запуска. Более строгие режимы добавляют
больше подтверждений, но это не должно скрывать расход:

```bash
agent-lifecycle metrics cost-check --receipt <lifecycle-cost-report.json>
```

Точные счётчики токенов должны поступать от принятого локального нормализатора
хоста. Данные тестовых образцов и консервативная оценка ядра остаются явно
оценочными и не подходят для S1/S2. Подробнее:
[локальный учёт токенов хоста](../reference/host-local-token-accounting.md).

Если требования процесса вышли за пределы режима, зафиксируйте причину. Сам по
себе дорогой запуск не является успехом: реализация и продуктовая проверка всё
равно должны пройти.

Встроенный набор эталонных задач предназначен только для синтетического
сравнения без записи. Его детерминированный результат выявляет ложную приёмку и
пробелы измерений. Промышленная готовность, уровень поддержки адаптера и
публикация релиза используют отдельные подтверждения. Подробнее: [оценка по
эталонным
задачам](../reference/reference-task-evaluation.md).

## Маленькие локальные модели

Для маленьких моделей сначала готовьте компактные снимки и артефакты:

- `goal summarize`: цель и следующий шаг;
- `runner status --target-window 4k-strict`: состояние выполнения;
- `report status-view --target-window 4k-strict`: обезличенный статус
  подтверждений;
- `metrics cost-check`: накладные расходы процесса.

Эти артефакты помогают выполнению. Они не заменяют полные подтверждения для
финальной проверки.

## Наблюдение за выполнением процессов

Каждый ограниченный ALK запуск внешнего процесса создаёт обезличенную
квитанцию `agent-process-execution-receipt.v1`. В ней указаны:

- монотонная длительность;
- время процессора, пиковая память и число процессов, если хост может их
  подтвердить; иначе у измерения будет статус `ESTIMATED` или `UNAVAILABLE`;
- признак тайм-аута и отмены;
- сведения об ограниченной повторной попытке;
- результат очистки группы процессов.

Для одного или нескольких запусков создайте локальный сводный отчёт:

```bash
agent-lifecycle metrics execution-report \
  --receipt work/evidence/process-receipt.json \
  --out work/evidence/execution-resource-report.json
```

Для нескольких запусков повторите `--receipt`. Неудачная или неподтверждённая
очистка переводит отчёт в `BLOCKED`; ALK не скрывает её новой попыткой.
Квитанция и отчёт не сохраняют аргументы команды, окружение, секреты или вывод
хоста. Контракт и различия платформ описаны в разделе [наблюдение за
выполнением процессов](../reference/process-execution-observability.md).

## Внешний контекст

Выгрузки внешней памяти являются подсказками, а не источником истины:

```bash
agent-lifecycle context external-import \
  --source work/context/project-memory.md \
  --citation "одобренная оператором выгрузка памяти проекта" \
  --out work/context/project-memory.external-context.json
```

Импортируйте только файлы, которые оператор выбрал явно. ALK не вызывает
MCP-серверы, сервисы поиска по базе знаний, провайдеров или CLI хостов, чтобы
получить память. Артефакты должны сохранять `sourceOfTruth: false`,
обезличивать секретоподобные значения и не раскрывать приватные локальные пути.

## Граница безопасности

Релизные и рабочие проверки должны соблюдать эти границы:

- не хранить приватные ключи, токены, cookie или локальные пути машины в
  отслеживаемых файлах;
- не использовать внешний контекст как доказательство жизненного цикла или
  источник истины;
- подтверждать уровень поддержки адаптера только артефактами, привязанными к
  хосту;
- не заявлять одобрение публичного каталога или промышленную готовность без
  внешнего подтверждения;
- не переносить хост-специфичную семантику в общие контракты ядра.

Локальный профиль внешней команды является явным исключением из обычного
маршрута без процессов, но не новым источником полномочий жизненного цикла.
Храните такие профили только в исключённом каталоге `.alk/host-launch/`,
сначала проверяйте структуру, затем готовность, разрешайте только точные имена
переменных окружения и используйте `start --launch` только с зафиксированной
идентичностью и выведенным профилем риска. Не помещайте текст задачи, команду
оболочки или секреты в `argvTemplate`. Подробнее: [локальный запуск внешней
команды](../reference/local-host-launch.md).
Для поставляемых профилей Codex, Claude Code и OpenCode перед основным запуском
требуйте подтверждение точной версии. Проверка версии не подтверждает расход
токенов; см. [запуск зафиксированной задачи через проверенный
профиль](../reference/qualified-host-launch.md).

Планирование по обычному тексту является отдельной операцией профиля. Текст
можно передавать только через ограниченный стандартный ввод; встроенные
ограничения внешнего CLI на запись и инструменты должны быть подтверждены, а
результат обязан завершиться состоянием `REVIEW_REQUIRED`. Считайте
`PLANNING_ONLY_UNSUPPORTED` окончательным отказом, пока нет подтверждения
ограничений для точной версии из реального запуска. Для этого маршрута
используйте полный набор подтверждений уровня поддержки адаптера и проверку
версии. Подробнее: [запуск адаптера только для
планирования](../reference/planning-only-launch.md).

Перед заявлением стабильного пакета используйте `agent-lifecycle contract check`
и релизные проверки безопасности. Уровень поддержки адаптеров берите из
матрицы поддержки; доступность модели является одним из входов полного набора
подтверждений `VERIFIED`.

Для выпуска исходного дерева проверяйте `tracked-release`, чтобы отчёт был
привязан к индексу Git и текущей ревизии. Не добавляйте
`--include-local-artifacts` в общий релизный шаг: этот флаг предназначен для
отдельной проверки подтверждений, чьи корни объявлены в `localArtifactRoots`.
Подробнее: [проверка нейтральности](../reference/neutrality.md).
