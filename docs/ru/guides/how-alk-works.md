# Как ALK работает с разными задачами

Agent Lifecycle Kit (ALK) решает задачу управления завершением работы кодовых
агентов. Он сохраняет связь между ожидаемым результатом, проверенным планом,
границами выполнения, подтверждениями и решениями о приёмке до тех пор, пока
работа не будет доказанно завершена или явно заблокирована. Исследование,
написание кода и запуск инструментов выполняет внешний кодовый агент; ALK не
заменяет агента и среду выполнения модели.

Это различие определяет порядок работы. Обычный текст, переданный в
`agent-lifecycle start`, становится проверяемым черновиком. Он не получает
полномочий на реализацию только из-за установленного плагина или наличия
параметра `--launch`.

## Участники процесса

| Участник | Ответственность |
| --- | --- |
| Пользователь или оператор | Определяет ожидаемый результат, принимает существенные решения и предоставляет внешние разрешения. |
| ALK | Хранит состояние жизненного цикла, полномочия плана, границы записи, проверки, подтверждения и итоговое доказательство. |
| Адаптер | Переводит переносимые действия ALK в команды конкретного хоста и оставляет секреты и телеметрию за пределами ядра. |
| Кодовый агент | Исследует, планирует, изменяет файлы и запускает инструменты в пределах утверждённой задачи. |
| Независимый проверяющий | Оценивает план или реализацию, не наследуя вывод исполнителя. |

## Общий жизненный цикл

```mermaid
flowchart LR
  request[Текст задачи, файл, тикет или запрос на проверку]
  intake[Черновой вход]
  plan[Проверенный план]
  freeze[Зафиксированные полномочия]
  execute[Работа внешнего агента]
  validate[Проверки и подтверждения]
  audit[Независимый аудит]
  proof[Принятый результат или явная блокировка]

  request --> intake
  intake --> plan
  plan --> freeze
  freeze --> execute
  execute --> validate
  validate --> audit
  audit --> proof
```

Полный путь нужен только тогда, когда требуется изменить продукт и доказать
завершение работы. Исследование, планирование и проверка могут остановиться
раньше: их результатом становится проверенный документ без заявления о
реализации.

## Выбор соразмерной глубины

ALK использует минимальный уровень жизненного цикла, который сохраняет
необходимое качество:

| Уровень | Когда применять | Обязательный контроль |
| --- | --- | --- |
| S0 | Одна ограниченная механическая задача, один исполнитель, повышенных рисков нет | Точная область записи и хотя бы один способ проверки. |
| S1 | Обычная продуктовая задача с одним потоком выполнения | Требования, критерии приёмки, подтверждения, проверки и влияние на выпуск. |
| S2 | Архитектура, безопасность, производительность, браузер, внешняя среда или несколько исполнителей | Полное владение, граф зависимостей, бюджеты, пределы контекста, проверки безопасности и финального аудита. |

Для небольшой одноразовой правки ALK может быть избыточен. Обычную работу не
следует переводить на S2 только ради дополнительных документов процесса.

## Запуск из текста или одного Markdown-файла

Единая команда принимает и классифицирует задачу:

```bash
agent-lifecycle start --adapter codex --text "Исследуй причину падения теста оплаты"
agent-lifecycle start --adapter codex --file task.md
```

В режиме `auto` команда возвращает `agent-lifecycle-start-receipt.v1`. Для
обычного текста или Markdown результат остаётся черновиком, который нужно
проверить. ALK может рекомендовать расследование ошибки или проверку
несколькими рецензентами, но рекомендация не включает обязательную контрольную
точку и не запускает реализацию.

Внешний агент может использовать навык `agent-workflow-orchestrator`, чтобы
провести запрос через жизненный цикл. Установка навыка предоставляет процедуру,
но только состояние и подтверждения показывают, была ли она действительно
выполнена.

## Только исследование или анализ

1. Запишите вопрос и ожидаемый результат в Markdown-файл.
2. Зарегистрируйте вход без права на реализацию:

```bash
agent-lifecycle start \
  --adapter codex \
  --mode research \
  --file research.md \
  --out work/research/start.json
```

3. Передайте задачу выбранному внешнему агенту. Ядро ALK в этой команде не
   вызывает модель.
4. Проверьте отчёт и завершите процесс. Не создавайте полномочия на изменение
   кода, если реализация не требовалась.

Полезным результатом здесь является проверенный исследовательский документ, а
не зафиксированный запуск реализации.

## План без реализации

Для одного файла задачи:

```bash
agent-lifecycle start \
  --adapter codex \
  --mode plan \
  --file feature.md \
  --out work/planning/start.json
```

Для папки с документами OpenSpec, Spec Kit, BMAD или Spec Kitty:

```bash
agent-lifecycle import plan \
  --source specs/checkout/ \
  --dialect spec-kit \
  --out work/planning/import.json
```

Внешний агент превращает черновой вход в пакет плана. До выдачи полномочий на
работу проверьте структуру плана и связь критериев приёмки:

```bash
agent-lifecycle plan completeness-check --manifest tasks/my-plan/plan.manifest.json
agent-lifecycle plan acceptance-check \
  --manifest tasks/my-plan/plan.manifest.json \
  --acceptance tasks/my-plan/acceptance-criteria.md
agent-lifecycle plan refs-check --manifest tasks/my-plan/plan.manifest.json
agent-lifecycle plan check \
  --manifest tasks/my-plan/plan.manifest.json \
  --lock tasks/my-plan/plan.lock.json \
  --require-completeness
```

Структурный статус `PASS` не заменяет независимую проверку. Перед фиксацией
плана уровня S2 его должен проверить отдельный рецензент.

## Проверка плана или архитектуры

```bash
agent-lifecycle start \
  --adapter codex \
  --mode review \
  --file proposed-plan.md \
  --out work/review/start.json

agent-lifecycle review-mesh recommend \
  --file proposed-plan.md \
  --out work/review/recommendation.json
```

Для обычной задачи достаточно одного независимого проверяющего. Несколько
рецензентов полезны, если задача объединяет разные области риска, содержит
спорные предположения или требует кворума. Результат проверки остаётся
рекомендательным, пока зафиксированный план не объявит его обязательным
подтверждением.

## Проверка изменений кода

1. Получите локальную ветку, запрос на слияние GitHub или GitLab.
2. Подготовьте устойчивый файл изменений вне ALK:

```bash
git diff origin/main...HEAD > work/code-review/diff.patch
```

3. Создайте `work/code-review/review-task.md` и укажите целевую ветку,
   ожидаемую архитектуру, области риска и путь к `diff.patch`.
4. Выполните `start --mode review`; при необходимости запросите рекомендацию
   командой `review-mesh recommend`.
5. Внешний агент или рецензенты изучают репозиторий и изменения. ALK фиксирует
   границу проверки и проверяет импортированные результаты, но сам не получает
   и не сливает запрос на изменение.

Подробные варианты для локальной ветки, GitHub, GitLab, известной и
неописанной архитектуры приведены в [сценариях проверки
кода](../code-review-workflows.md).

## Исправление ошибки

```bash
agent-lifecycle start \
  --adapter codex \
  --text "Найди и исправь периодическое падение обратного вызова оплаты" \
  --out work/bug/start.json
```

Для задачи с признаками ошибки ALK может рекомендовать профиль расследования.
Зафиксированный план исправления должен потребовать воспроизведение до правки,
устойчивый отпечаток ошибки, ограниченный журнал гипотез, минимальную
обоснованную правку и регрессионную проверку того же отпечатка. Автоматическое
распознавание остаётся рекомендацией, пока проверенный план не включит эти
контрольные точки.

## Реализация зафиксированной задачи

Реализация намеренно отделена от приёма обычного текста:

1. Проверьте и зафиксируйте план вместе с файлом блокировки.
2. Создайте или загрузите состояние рабочего цикла, связанное с этим планом.
3. Определите стратегию выполнения с учётом риска для конкретной задачи.
4. Начните задачу с тем же отпечатком профиля риска.
5. Передайте внешнему агенту только назначенный пакет работы.
6. Сохраните результат задачи и подтверждения.
7. Проведите независимый аудит реализации до приёмки задачи.
8. Завершайте запуск только после приёмки всех задач и прохождения финальных
   контрольных точек.

Единая команда может передать уже связанный запрос:

```bash
agent-lifecycle start \
  --adapter codex \
  --mode implement \
  --file work/run/adapter-run-request.json \
  --risk auto \
  --risk-profile-out work/run/risk-profile.json
```

Обычный текст в режиме `implement` отклоняется. Команда `start` не создаёт
зафиксированный план и не утверждает его автоматически.

## Запуск внешней команды

По умолчанию процесс запускает адаптер или обёртка хоста. Локальный запуск
через ALK требует исключённый из Git профиль с точной версией, предварительную
проверку, явный параметр `--launch`, данные зафиксированной задачи и профиль
риска:

```bash
agent-lifecycle adapter launch-profile \
  --adapter codex \
  --repository-root /path/to/agent-lifecycle-kit \
  --out .alk/host-launch/codex.json

agent-lifecycle host-launch preflight \
  --profile .alk/host-launch/codex.json
```

Встроенные дескрипторы сохраняют состояние `WRAPPER_ONLY`. Дескриптор,
установленный плагин или обычный текст задачи не дают полномочий на создание
процесса. Подробнее: [локальный запуск внешней
команды](../reference/local-host-launch.md) и [квалифицированный
запуск](../reference/qualified-host-launch.md).

## Проверка несколькими рецензентами

1. Получите рекомендацию командой `review-mesh recommend`.
2. Подготовьте пакеты рецензентов командой `review-mesh prepare`.
3. Запустите каждого рецензента в его хосте за пределами ядра ALK.
4. Импортируйте очищенные результаты командой `review-mesh import-result`.
5. Объедините выводы и создайте подтверждение кворума.
6. Считайте кворум блокирующим только для этапов, указанных в зафиксированном
   плане.

Полный набор команд приведён в [руководстве по проверке несколькими
рецензентами](../review-mesh-workflow.md).

## Возобновление работы

```bash
agent-lifecycle start \
  --adapter codex \
  --resume <session-id> \
  --session-root .alk/adapter-sessions
```

Идентификатор относится к состоянию ALK, а не к диалогу Codex, Claude Code или
OpenCode. При возобновлении проверяются адаптер и происхождение состояния;
полномочия не восстанавливаются из истории переписки.

## Соразмерность затрат процесса

ALK разделяет непосредственную реализацию, проверку продукта, соблюдение
процесса и координацию. Отчёт строится по существующим подтверждениям:

```bash
agent-lifecycle metrics cost-report \
  --mode standard \
  --artifact work/run/usage.json \
  --artifact work/run/task-review.json \
  --out work/run/lifecycle-cost.json

agent-lifecycle metrics cost-check --receipt work/run/lifecycle-cost.json
```

Для ограниченной работы используйте S0 или режим `light`, для обычной
продуктовой задачи — S1 или `standard`, а строгий процесс применяйте только при
подтверждённом риске. Детерминированные команды ALK не расходуют токены модели,
но работа рецензентов и координация могут их расходовать.

Текущая проверка ограничивает категорию `pipelineCompliance`, а координацию
показывает отдельно. Поэтому один такой отчёт ещё не доказывает, что все
служебные затраты занимают меньше половины реального запуска. Для обоснованного
вывода нужны полные данные хоста по этапам и совместная оценка обеих категорий.

Если служебная работа преобладает в задаче S0 или S1, следует убрать
дублирующие проверки, разделить слишком широкий план, сократить необязательную
перепроверку или не применять ALK к этой задаче. Нельзя снижать обязательный
уровень качества только ради более выгодных показателей.

## Что считается завершением

ALK достигает цели, когда существует требуемый продуктовый результат,
проверено обязательное поведение, независимый аудит принял подтверждения, а
итог можно воспроизвести. Большое количество служебных артефактов без решения
исходной задачи не считается успехом.
