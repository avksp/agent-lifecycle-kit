# Рабочий процесс исследования

[English version](https://github.com/avksp/agent-lifecycle-kit/blob/main/docs/guides/research-workflow.md)

Используйте этот процесс, когда перед планированием нужно изучить архитектуру,
сравнить внешние материалы, разобраться в проблеме или собрать выводы от
нескольких независимых источников.

## Когда это нужно

Пакет исследования нужен, когда результат должен оставаться проверяемым или
когда в работе участвуют несколько людей или моделей. Для короткой личной
заметки достаточно обычного файла задачи. Исследовательские материалы полезны,
когда для утверждения нужно сохранить источник, цитату и понятное происхождение
данных.

## Шаг 1. Соберите материалы

Храните исходные документы в рабочей области оператора. Если нужно проверить
точную цитату, подготовьте для каждого источника отдельный снимок в кодировке
UTF-8:

```text
work/research/
  research-evidence.json
  snapshots/
    source-1.txt
    source-2.txt
```

Переносимый пакет хранит ссылки, отпечатки и сведения о редакции. Полные
документы, промпты, секреты, имена провайдеров и моделей в него не включаются.
Пакет создаёт адаптер или инструмент оператора по схеме
`agent-research-evidence-package.v1`; ALK проверяет пакет, но не загружает
содержимое по URL и не делает вывод по одной ссылке.

## Шаг 2. Проверьте пакет

```bash
agent-lifecycle research validate \
  --package work/research/research-evidence.json \
  --snapshot source-1=work/research/snapshots/source-1.txt \
  --snapshot source-2=work/research/snapshots/source-2.txt \
  --out work/research/validation.json
```

Передавайте `--snapshot SOURCE_ID=PATH` только для источника, цитату которого
нужно проверить локально. Если снимок не передан, результат будет отмечен как
`UNAVAILABLE` и попадёт в список пробелов, а не будет ошибочно принят за
проверенную цитату.

## Шаг 3. Получите сводку

```bash
agent-lifecycle research summary \
  --package work/research/research-evidence.json \
  --validation work/research/validation.json \
  --out work/research/summary.json
```

Сначала проверьте поля:

- `status` — прошёл ли пакет детерминированную проверку;
- `supportedClaims` — утверждения с совпавшей цитатой без статуса `stale` или
  `disputed`;
- `evidenceGaps` — утверждения, которым не хватает источника или проверенной
  цитаты;
- `duplicateGroups` — источники, которые нельзя считать независимыми;
- `lifecycleCounts` — распределение записей по статусам `draft`, `reviewed`,
  `accepted`, `stale` и `disputed`.

## Шаг 4. Используйте результат при планировании

Рассматривайте сводку как проверенный вход для черновика спецификации. На её
основе сформулируйте требования, допущения и критерии приёмки. Для каждого
важного вывода укажите, нужна ли проверка тестом, просмотром кода или
подтверждением специалиста. Затем выполните обычное планирование ALK:

```bash
agent-lifecycle start --adapter <adapter-id> --file task.md --mode plan
agent-lifecycle plan check --manifest <папка-плана>/plan.manifest.json
```

Проверка исследования не фиксирует план и не даёт полномочий на реализацию.
Утверждение может стать требованием, но частью жизненного цикла оно становится
только после проверки спецификации, приёмки плана и его фиксации.

## Несколько моделей и источников

Разные адаптеры или модели могут готовить отдельные записи источников и
утверждений. Не объединяйте их выводы до фиксации происхождения и цитат.
Затем Review Mesh может подготовить пакеты проверяющих и свести результаты.
Валидатор исследования работает локально: он не обращается к моделям и не
решает, чьё заключение правильнее.

## Частые случаи

| Случай | Рекомендуемый вход | Следующий шаг ALK |
| --- | --- | --- |
| Исследование архитектуры | Источники, утверждения, цитаты и связи зависимостей | Подготовить раздел архитектуры и вопросы для проверки плана. |
| Сравнение внешних проектов | Отдельный источник для каждого проекта, связи дубликатов и производных материалов | Подготовить ограниченное сравнение и отметить неподтверждённые выводы. |
| Разбор инцидента или ошибки | Наблюдения, воспроизведение и снимки источников | Подключить профиль Bug Forensics для воспроизведения и регрессионного подтверждения. |
| Долгое исследование перед реализацией | Периодические проверенные пакеты с ограниченными сводками | Прикреплять сводки к текущему черновику и повторно проверять изменившиеся допущения. |
| Независимая проверка | Отдельные записи источников для каждого проверяющего или адаптера | Использовать Review Mesh для назначения, импорта, объединения и необязательного кворума. |

См. [проверку исследовательских материалов](../reference/research-evidence.md)
для контракта, правил безопасности и полного описания результатов.


## Проверка решений до запуска задачи

Добавьте в workstream необязательное поле `decisionResearch`, если перед
исполнением нужно сохранить сравнение решений. Проверка относится к объявленным
замороженным входам. Она не доказывает глобальную оптимальность решения. Без
этого поля задача сохраняет прежнее поведение.

1. Выберите профиль не ниже уровня замороженного плана. Для S0 обязателен
   `requirement-fit`, для S1 также `security`, для S2 также `architecture`,
   `resources` и `feasibility`. Каждый обязательный критерий требует оценки и
   обоснования, в том числе при неприменимости. Можно добавить критерии проекта.
   Метрики поставки DORA и приоритеты относятся к проекту или внешней SDLC,
   а не к универсальной политике ALK.
2. Объявите ограниченные входы и запись исследования в `planFiles`. Каждый
   вход также должен быть в `contextRefs` workstream. В descriptor используйте
   уникальные имена файлов без каталогов и SHA-256 точных исходных байтов.
   Включите `specification.source`, если он задан. Область всего workspace или
   незамороженные live-входы не поддерживаются.
3. Запишите варианты, выбранное решение, оценки, владельца и конечный бюджет
   исследования. Включите вариант `NO_CHANGE`. Решения `KEEP`, `SIMPLIFY` и
   `REPLACE` допускают продолжение; `SPLIT` и `STOP` требуют пересмотренного
   проверенного плана. Запись не имеет полномочий lifecycle или review.
4. Вычислите привязки при подготовке DRAFT. Для JSON-файлов, проходящих через
   `freeze-prepare`, используйте canonical JSON с завершающим переводом строки:
   существующий writer приводит JSON к этому виду. Считайте хеш после окончательного
   форматирования. Сохраните именно те байты, которые хешировали. Native guard
   не принимает нормализованный хеш вместо исходного.
5. Подготовьте кандидат, получите независимый plan review, создайте reviewed
   lock и выполните adoption штатным маршрутом. Подготовка переносит opt-in
   ссылки контекста в inventory кандидата. Перед стартом ALK проверит реальные
   ограниченные байты входов/записи и принятый независимый review.

В core есть детерминированные функции для подготовки DRAFT:

```python
from hashlib import sha256
from agent_lifecycle.contracts import canonical_bytes
from agent_lifecycle.research.preflight import (
    decision_input_digest, decision_policy_digest, decision_scope_digest,
)

policy = workstream["decisionResearch"]
policy["scopeDigest"] = decision_scope_digest(manifest, workstream)
policy["inputDigest"] = decision_input_digest(policy["inputs"])
policy["policyDigest"] = decision_policy_digest(policy)
for key in ("scopeDigest", "inputDigest", "policyDigest"):
    record[key] = policy[key]
record_bytes = canonical_bytes(record) + b"\n"
policy["record"]["sha256"] = sha256(record_bytes).hexdigest()
```

Здесь `manifest`, `workstream`, `policy` и `record` — полные объекты DRAFT.
До review сохраните `record_bytes` в объявленный файл. Эти функции не создают
review, lock или разрешение на исполнение. Для обновления доказательств нельзя
редактировать замороженные файлы или workflow state.

Жёсткие потолки v1: восемь входов, 65 536 байт на вход, 262 144 байта записи,
три точки входа в код, три варианта, один probe и два раунда review. Профиль
может уменьшить лимиты. Конечный бюджет задаёт `maxCommands` (1–100),
`maxActiveSeconds` (1–3600) и минимум один `reservedCommands`, меньше
`maxCommands`. Неизвестный фактический расход имеет статус `UNAVAILABLE` и null
в `usedCommands`/`usedActiveSeconds`. Значения `DECLARED` остаются сообщением,
а не telemetry провайдера. Проверка не измеряет все вызовы моделей, хоста и тестов.

Неизменные привязки и исходные байты позволяют переиспользовать исследование.
Новая объявленная база, контракт выбранной задачи, вход или профиль меняют
соответствующую привязку. В scope не входят физические каталоги контейнера,
байты планового результата и посторонние задачи. Отсутствующие, устаревшие,
опасные, превышающие лимит или неподдерживаемые данные вызывают отказ до старта.
Прямой старт и `workflow continue` используют один native guard. Отказ не
запускает исследование моделью или автоматический повтор; прежние расходы и
часы сохраняются.

Необязательный `evidencePackage` должен пройти свой validator и иметь реальные
снимки всех объявленных в пакете источников с подтверждёнными цитатами. Общего
PASS пакета с недоступными доказательствами цитат недостаточно для этого допуска.
Оба wire-контракта описаны в [research evidence](../reference/research-evidence.md).
